## 0. 一句话目标

把"**一次评估 N 个分支 → N 个工厂方块**"改成"**一次评估 → 1 个工厂（内部 N 个互斥模式）**"，
堵住"廉价垃圾 + 并行输入方块 → 产线扩张（N 倍产能）"的漏洞。

## 1. 铁律（任何实现者不得违反，违反即回退）

| # | 铁律 | 检查方式 |
|:--|:--|:--|
| **I1** | 一次评估固化**恰好一个**工厂方块 | grep 固化循环里是否还有 `offset(0, i, 0)` 堆叠 |
| **I2** | **严格互斥**：任一 tick 至多一个模式在兑换 | `tick()` 里只能选出一个激活模式 |
| **I3** | 无匹配模式 → 空闲（不消耗、不产出、不推进进度）；**不做兜底模式** | 无触发物品且无默认模式时 `lastSuccess=false` 并 return |
| **I4** | 模式判定**确定性**（同输入必得同模式） | 候选取 `min(index)` |
| **I5** | 应力**保守合并为一份**：消耗取最大、供给取最小；不随模式切换 | 档案写入点仍只有一处 |

## 2. 接口契约（冻结；改动需 Lead 同意并更新本节）

### 2.1 工厂 BE 的 NBT 结构

**共享层（跨模式，顶层）**——容器是**所有模式的并集**，容量取**各模式最大值**：

```
installed / room_code / restore_state / restore_machine / preview   ← 不变（预览仍只存一份）
input_items / output_items / burner_fuel_items                      ← Container：签名 → {容量, 存量, 模板}
input_fluids / output_fluids
input_energy_capacity / input_energy_amount / output_energy_capacity / output_energy_amount
mode_count        : int          ← 新增。缺失 ⇒ 旧档，按"单模式 + 顶层平铺表"读
modes             : ListTag      ← 新增。每元素一个 CompoundTag
active_mode       : int          ← 运行时状态（可选持久化）
```

**模式层（`modes[i]`）**——每模式只存"自己那张表"，不含容器：

```
trigger          : string        ← 触发物品身份签名（ItemIdentity）；"" / 缺失 = 默认模式
verdict          : string        ← "RATE" | "REPLAY"
progress         : int           ← REPLAY 秒槽指针（切走时归零）
# RATE
input_item_rates / output_item_rates / input_fluid_rates / output_fluid_rates
input_energy_rate / output_energy_rate
normal_burn_demand / super_burn_demand
# REPLAY
input_item_patterns / output_item_patterns / input_fluid_patterns / output_fluid_patterns
input_energy_pattern / output_energy_pattern
pattern_length   : int
```

**旧档回退**：无 `mode_count` ⇒ 合成单个模式 `{trigger:"", verdict: replay_mode ? REPLAY : RATE, progress: replay_current_second}`，
表内容取顶层平铺键 ⇒ **行为与 0.4.31 逐位一致**。

### 2.2 运行时实现要点（**关键设计，避免下游大改**）

共享容器 + "当前模式的表"这个结构，与现有代码天然契合：`inputsSatisfied()`（`FBE:754-768`）与
`tickRateContinuous()`（`FBE:681-693`）本来就是"**遍历容器 → 用 `rateMap.get(签名)` 查表 → `null` 就跳过**"。
⇒ 只要把 8 张表字段改成**指向当前模式表的引用**（引用赋值，无拷贝），下游逻辑**一行都不用改**：

```java
private void setActiveMode(int index) {
    activeMode = index;
    Mode m = modes.get(index);
    this.inputItemTickRates  = m.inputItemTickRates;    // 引用赋值
    this.outputItemTickRates = m.outputItemTickRates;
    this.inputFluidTickRates = m.inputFluidTickRates;
    ...  // 其余同理；replayMode / patternLength 也随模式取
}
```

**模式选择**（每 tick，`tick()` 开头）：

```
候选 = { i | modes[i].trigger 非空 且 输入容器中该签名 amount ≥ 1 }
激活 = 候选非空 ? min(候选) : (存在默认模式 ? 该默认模式 : 空闲)
```

### 2.3 跨模块 API（**已定死**）

**① `EvaluationVerdict` 与 `Result` 提升为 `public`**（T3 负责）
理由：`block` 包需要读它。`FactoryBlockEntity` 已跨包依赖 `EvaluationTrace.FlowKey`，不是新问题。

**② `Result` 新增末位组件 `triggerItems`**（T3 负责）

public record Result(String verdict, String rejectReason,
                     Map<EvaluationTrace.FlowKey, Double> inputRates,

                     Map<EvaluationTrace.FlowKey, int[]> replayOut,
                     Map<EvaluationTrace.FlowKey, ItemStack> inputItemTemplates,
                     Map<EvaluationTrace.FlowKey, ItemStack> outputItemTemplates,
                     double inputEnergyRate, double outputEnergyRate,

                     double normalBurnDemandPerSecond, double superBurnDemandPerSecond,
                     String detail,

**③ `decide(...)` 增加末位参数 `List<String> triggerItems`**（T3 负责）
构造点共 3 处：`rateResult`、REPLAY 分支、`reject`（`EvaluationVerdict:84/106/116`）。

**④ 工厂侧入口**（T1 负责）

**⑤ 固化前可触发性校验**（T3 提供静态工具，T2 调用）

```java
/**
 * 校验每条分支的 triggerItems 是否都在该分支的输入表中；
 * 返回不可触发项的**本地化**说明（空列表 = 全部可触发）。
 *
 * ⚠️ 必须返回 Component 而**不是** String —— 物品名要按玩家语言渲染，
 *    一旦在服务端拼成 String 就永久丢失本地化（本项目已有先例教训）。
 *    显示名来源：Result.inputItemTemplates() 中按签名取模板 → ItemStack.getHoverName()；
 *    模板缺失时回退用 id 构造 ItemStack 再取名。
 */
static List<net.minecraft.network.chat.Component> EvaluationVerdict.untriggerableModes(List<Result> modes);
```

**⑦ 提示文案的渲染约束**（对所有失败/取消路径）

- `EvaluationManager.requestCleanup(...)` 的 key 最终由 `rollbackReason()` 以 `Component.translatable(key)` **无参**渲染
  ⇒ 走该路径的键**必须无参**；需要参数化的细节（分支 / 物品名）由调用方**另行 `notifyOwner(...)` 一条带参数的消息**承载。
- 因此新增两个键：

| 键 | 参数 | 用途 |
|:--|:--|:--|
| `message.createcmpor.evaluation.branch_failed` | `%1$s`=触发物品本地化名（已拼好，多物品用本地化分隔符）、`%2$s`=失败原因 | 分支评估失败（`eval-side`，用户明确要求） |
| `message.createcmpor.evaluation.untriggerable_mode` | **无参** | 固化取消的**总述**（`solidify` 走回滚通知） |
| `message.createcmpor.evaluation.untriggerable_branch` | `%1$s`=分支序号（从 1 起）、`%2$s`=物品本地化名 | **逐条明细**（由 `untriggerableModes` 生成，`solidify` 拼到总述之后） |

- `message.createcmpor.evaluation.solidify_blocked` 在删掉堆叠失败分支 + 空间预检后**成为死键**，由 `surfaces` 一并删除。

**⑥ `triggerItems` 采集点**（T3 负责）
`EvaluationScheduler.activateIoBlocks`（`ESch:534-550`）设置 `setBranchIndex(...)` 的同一处，
读取该副本内**所有** `PARALLEL_INPUT` 的 `items.get(branchIndex)` 身份签名（去重；越界条目忽略）。
并行路径每 lane 各自采集；串行路径每分支各自采集。

### 3.2 全局约束（写进每个 teammate 的 prompt）

- **不许改** `evaluation/EvaluationManifest.java` 的分支间清理回流逻辑（`resetForBranch` / `copyForBranchTarget`）——那是**评估侧**机制，与本重构无关（风险 R6）。
- **不许**全局重命名 `branch_index`：**同名键**同时属于 `ParallelInputBlockEntity`（-1 语义）与 `FactoryBlockEntity`（0-based）（风险 R1）。
- 沙箱下 `gradlew` 会因无法写 `C:\Users\<user>\.gradle` 而失败——**不要尝试**；构建由 Lead 用 `CreateCMPOR [build]` 执行。
- ⚠️ **`get_file_problems` 不可作为验收证据**（2026-10-05 实测）：对被**外部改动过**的文件它返回 0 error / 0 warning，而同一时刻 `get_symbol_info` 明确报"找不到方法调用 `factory.installModes(results)` 的候选者" ⇒ 它的语义分析是陈旧/未生效的。
  ⇒ **真编译只能由 Lead 跑 `CreateCMPOR [build]`**；队友自检请用**文本级断言**（grep 函数名/键名/结构）与 `get_symbol_info` 逐点核对。
- 大文件**禁止**"整文件读→写重建"（会静默截断，项目已踩过坑）；用小块 `edit`。
- 多人并行时 **lang 键名必须唯一仲裁**（已发生过一次撞车：`untriggerable_mode` 被两方以不同参数使用）；新增键一律先报 Lead 统一，再落到 `surfaces`。
