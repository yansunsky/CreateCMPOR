## 2026-08-27：应力输出显示修复——改走原生通知链路（0.3.35，构建通过）

**用户反馈**：NBT AddedCapacity:2051 已正确（服务端网络对）但护目镜/应力渲染始终 0；"方法错误"。

**根因**（源码核实）：Create 原生 `updateGeneratedRotation()`（GeneratingKineticBlockEntity line 89-110）在 `speed != 0` 时调用 **`notifyStressCapacityChange`**（**带客户端同步**）——这才是正确链路。而我：
- 0.3.33/0.3.34 定时 `updateCapacityFor` 硬塞绕过原生活动通知（服务端对、客户端不同步）
- line 386 自愈条件 `getTheoreticalSpeed() != getGeneratedSpeed()` **恒等**（源的理论速度=生成速度）→ 从不触发 `updateGeneratedRotation`

**修复**：撤销定时 updateCapacityFor；tick 末尾检测 **lastSuccess 状态变化 → `updateGeneratedRotation()`**（走原生 applyNewSpeed + notifyStressCapacityChange → 客户端同步）；新增 `lastSuccessReported` 快照字段（首 tick 从 false 起步也补齐）。
- 版本 0.3.34 → 0.3.35

## 2026-08-27：应力输出容量显示不更新修复（0.3.33，构建通过）

**用户反馈**：应力输出功能 OK 但 Create 自带应力值渲染（蓝色字）显示 0，实际已有输出。

**根因**：工厂容量随运转状态动态变（lastSuccess 门控），但 `updateCapacityFor`（上报网络容量）**只在 `onSpeedChanged`（速度变化）调用**——恢复供料/暂停变化若理论速度不变则不触发 → 网络容量缓存旧 0 → 客户端渲染 0。

**修复**：`tick()` 末尾（兑换后）输出型且已入网（isProvide && hasNetwork && isSource）→ **每 tick 主动 `updateCapacityFor(this, calculateAddedStressCapacity())`** —— 容量随 lastSuccess 实时同步网络/客户端。
- 版本 0.3.32 → 0.3.33

## 2026-08-27：应力输出未绑定运转状态修复（0.3.32，构建通过）

**用户反馈**：应力输出即使不满足输入物品条件和输入热值条件也能输出剩余应力 —— bug。

**调研**：输出型工厂（profile.isProvide()，outputSU>0）作为应力源：`getGeneratedSpeed`（返回 outputRPM，line 1374）+ `calculateAddedStressCapacity`（提供容量）—— **完全独立于运转状态**；暂停（inputsSatisfied/burnerSatisfied 不满足 → lastSuccess=false）只挡**产物兑换**（tickRateContinuous/replayIsReady），**不影响应力输出** → 停机也持续输出。

**修复**：
- `lastSuccess` 默认 true → **false**（未运转/未安装前不输出）
- `getGeneratedSpeed`：`!profile.isProvide() || !lastSuccess` → 返回 0（暂停时无转速 → 网络无转速、下游机械停、容量自动 0）—— `calculateAddedStressCapacity` 依赖 speed=getTheoreticalSpeed（已 gate）无需改
- 效果：缺料/燃料不足/输出满仓暂停时，工厂**不生成转速 → 不输出应力**；恢复运转（lastSuccess=true）自动恢复
- 版本 0.3.31 → 0.3.32

## 2026-08-27：燃烧测试——独立燃料槽重构 + 伪空修复 + 桶不返还（0.3.26，构建通过）

**用户反馈**：① 溜槽投料失败（原版漏斗可以，猜测一次性 16 个）② 熔岩桶变成产物不断产出（与预期不符）③ 建议单独燃料槽（但不知道如何导入）④ 创造燃烧室/S0 全空/tooltip 视觉测试**通过**。

**根因（源码核实）**：
- **溜槽投料失败**：Create `ChuteBlockEntity`（line 379）向下传物用 `ItemHandlerHelper.insertItemStacked(capBelow, item, simulate)` —— 该 helper **只对同物品堆合并或对空堆槽插入**（`getStackInSlot().isEmpty()` 探测）；工厂 `getStackInSlot` 对空槽返回 `max(1, amount)=1` **伪非空堆** → 溜槽找不到可插入槽 → 失败（原版漏斗逐槽直接调 insertItem 所以能进）
- **熔岩桶产物污染**：`returnEmptyBucket` 把空桶塞进**输出缓存** → 被当产物持续生成

**0.3.26 重构（用户方向：独立燃料槽，与输入/输出缓存解耦）**：
- **独立燃料仓** `burnerFuelItems`（Map<物品,Container>）；burn 模式 handler **末位追加 1 个燃料槽**：`getStackInSlot`=燃料仓首堆（空=EMPTY）、`insertItem(燃料槽,合格燃料)`→燃料仓、`isItemValid` 通过、`extractItem(燃料槽)` 禁止（只进不出）
- **伪空修复**：`getStackInSlot` 输入/输出空槽改返回 **EMPTY**（不再 max(1,amount) 伪 1）→ insertItemStacked 类自动化（溜槽/管道）能正确探测空槽插入（先匹配输入槽→输出槽→燃料槽）
- **熔岩桶直接消耗**（同 Create 燃烧室语义，移除 returnEmptyBucket）→ 无产物污染
- NBT `burner_fuel_items` 持久化；installRates/installPatterns 安装清空燃料仓
- **投料方式**：任意**非轴面**（isFactoryIoFace）漏斗/溜槽/管道均可（多槽遍历落燃料槽）
- 测试清单 docs/33 更新（1/5 🔧 待复测，其余 ✅）
- 版本 0.3.25 → 0.3.26

## 2026-08-21：io_extension 无法取产物修复——SHAFT_BY_FACE 方向反了（0.2.33，构建通过）

- 旧代码 accumulateFactory 用 `Direction.getNearest(worldPosition - factoryPos)`（工厂→拓展方向）检查工厂面向拓展的面，方向是对的——本次修复与之一致。

## 2026-08-20：三扫描防刷兜底规则重定义（需求确认版，待实现 0.2.24）

### 背景
用户重新定义了三扫描的用途：**三扫描是防玩家欺骗评估的兜底手段**。S0 初次扫描的真正作用是**过滤中间产物**（此前理解有误）。实测发现评估结束统计了大量中间产物（被当成产物）。

### 需求确认（经两轮追问，用户逐条确认）
- **扫描时机**：S0 在 **IO 激活前**扫描（房间未开工初始态）；S1=预热结束基线；S2=评估结束（IO 已停）终态。
- **产物**：key ∈ **输出方块实际 trace 收集到的种类**（`series.outputTotal>0` 的物品/流体集合，**不是配置的过滤白名单**）且净变化 > 0 → 输出。数量 = `net=(S2-S1)+O-I`。
- **中间产物**：key ∉ 输出种类，且 S0 无、S1 有、**且无 IO 输入流量（`ioIn==0`）** → **完全忽略**（即使被下游机器消耗也不计输入）。**⚠️ 0.2.24 实机 bug（已修复）**：最初未加 `ioIn==0` 条件，导致经 IO 输入的原料（圆石）在预热期积压到 S1 容器后，被误判为中间产物而忽略 → 工厂凭空产出安山合金。修复：中间产物判定必须排除有 IO 输入流量的外部原料。
- **消耗**：非中间产物的 key，`S1-S2` 净减少 → 输入（如煤 S1=40→S2=10 → 输入 30；预热期 S0→S1 烧的 10 不计）。
- **边界 1-A**：S0 有该物品（非输出种类）→ 不算中间产物，整体按初始库存处理。
- **边界 2-A**：输出种类物品净减少也按消耗处理（减少=消耗对输出种类同样适用）。
- **边界 3-B**：S0 全空判定需**物品+流体+能量全空**才触发简化路径。
- **S0 全空简化**：全空 → 完全不用 S1/S2 容器对比，工厂输入=IO 输入 trace、输出=IO 输出 trace。
- **防复制陷阱**：流体必须纳入全空判定——匠魂金属溶液预存储液罐，若只看物品，抽到输出方块即凭空复制新流体。
- **影响范围**：RATE（`auditRates`）+ REPLAY（`netBalance`）都按此规则改。

### 关键实现点
- S0 扫描前移到 `activateIoBlocks` 之前。
- "输出种类集合"从 trace 的 `series.outputTotal > 0` 提取（实际收集到的，非配置白名单）。
- 中间产物判定：非输出种类 且 S0 无该 key 且 S1 有 → 完全忽略。

## 备注：Mesa 软件渲染（环境性修改）
为在无 GPU 的 Windows Server 上运行 runClient，将 Mesa3D 26.1.1（llvmpipe）的 `opengl32.dll`、`libgallium_wgl.dll`、`dxil.dll` 复制到了 `C:\Program Files\zulujava\jdk-21\bin\`。这是开发环境的渲染兜底，**与模组本身无关**，正式服务器/有 GPU 的客户端无需此操作。`build.gradle` 的 client run 配置同时设置了 `GALLIUM_DRIVER=llvmpipe`、`LIBGL_ALWAYS_SOFTWARE=1`、`MESA_GL_VERSION_OVERRIDE=4.6` 等环境变量。
