## 2026-08-22：新想法考察记录（便携工厂遏制 / 评估进度显示 / io_extension Ponder）— 未实现

**背景**：玩家不评估空间，把压缩空间直接当"便携工厂"挂机产出。用户不反对这个玩法本身，但需要遏制"无玩家仍产出"。同时收到两个补充需求。以下为可行性考察（源码确认，非实现）。

### ① 遏制便携工厂：空间维度 tick 控制 / 无玩家强制卸载
**机制权威确认**（EvaluationTicketManager 64-69 行注释，开发时源码核实）：
- 空间维度 = `compactmachines:compact_world`（`CompactDimension.LEVEL_KEY`，core-api）
- **MC 原生 emptyTime 门控**：`ServerLevel.tick` 实体/方块 tick 条件 = `players 非空 || hasForcedChunks || emptyTime < 300`（300 tick = 15 秒）→ **无玩家 + 无 forced chunk + 15 秒，实体/方块自动停 tick**
- 玩家绕过途径：① 玩家待在空间里（players 非空，正常玩法）；② **forced chunks**：CM 房间 chunkloader 升级（`ChunkLoaderUpgradeComponent` → `TicketController.forceChunk(level, upgradeID, x, z, true, true)`）、vanilla `setChunkForced`、其他 force-load 模组
- 我们自己的 eval_world 就是靠 `setChunksForced`（forced chunk 模拟玩家加载）让无玩家维度保持 tick——与玩家"便携工厂"用的机制**完全相同**

**可行方案**：
- 方案 A（零代码）：依赖原生 emptyTime 门控，只防"未 force load"情况；chunkloader 可绕过——不满足"即使其他强制加载模组也要停"
- 方案 B（推荐考察，mixin）：`mixin ServerLevel.tick` 对 `CompactDimension.LEVEL_KEY` 且无玩家时，**无视 hasForcedChunks 强制跳过实体/方块 tick**（玩家在空间里时正常）。可彻底遏制所有 force-load 模组。**需实验验证**影响面
- 方案 C（更激进，mixin 卸载）：无玩家超时后移除 compact_world 所有 chunk tickets + forced 状态（跨模组 ticket 不好动，难度高）

**风险/注意**：
- 有玩家时必须正常 tick（玩家在房间内操作是正常玩法）
- 评估流程不受影响：源房间冻结克隆到 eval_world，compact_world 停 tick 无碍；eval_world 有自己的 forced chunks
- CM 传送（玩家进出）在玩家在场时正常
- **待用户决策**：遏制强度（仅依赖原生 / mixin 无视 forced chunks / mixin 卸载）

- 模板注册表 key：`compactmachines:room_templates`；`RoomTemplate.CODEC` 字段 `dimensions`（RoomDimensions.CODEC，可单 int 或 {width,depth,height}）/`color`/`structures`/`floor`。
- basic_templates 注册：CM `CMFeaturePacks.addFeaturePacks`（TOP + required=false 可选）；CreateCMPOR `onAddPackFinders` 已注册为 TOP + always-active。
- **覆盖方案**：可在 createcmpor jar 内建 `data/compactmachines/datapacks/...` 并用 `AddPackFindersEvent` 注册 TOP 数据包（packLocation path 是 jar 内 resources 路径），内容覆盖 `data/compactmachines/room_templates/*.json`。javadoc 确认 TOP=高优先级；但"同 TOP 时后添加者是否覆盖先添加者"的加载顺序细节**未完全确认，需实验验证**。
- `GraphChunkManager` 无尺寸硬上限（按 boundaries AABB 动态算 chunk，45 已跨 chunk，64 同理可行）。
- **用户决定：暂缓，以后再思考怎么处理。**

## 2026-08-21：io_extension 无法取产物修复——SHAFT_BY_FACE 方向反了（0.2.33，构建通过）

**用户实测**：io_extension 应力传递正常，但漏斗无法从它身上取出所连工厂方块内的产物（工厂也是用应力接口面连接的）。

**根因（源码确认，非猜测）**：BFS 里工厂开口面判断方向反了。`getReachableFactories()` / `factoriesFromEnd()` 用 `SHAFT_BY_FACE.get(d)`，其中 d 是 **io_extension→工厂** 的方向，但工厂面向 io_extension 的那一面是 **`d.getOpposite()`**。对照 Create `RotationPropagator.connectedByAxis`：从 A 到 B，B 检查的是 `direction.getOpposite()` 面。因此当 io_extension 在工厂上方（竖直堆叠）时：d=DOWN，检查 SHAFT_DOWN，但实际开口的是 SHAFT_UP → 找不到工厂 → capability 返回 null → 漏斗拿不到。
- **为什么应力正常**：Create 的 hasShaftTowards 双向检查用正确方向（direction.getOpposite()），应力网络连接成功；只有我们自己的 BFS 方向错了，只影响 IO。
- 旧代码 accumulateFactory 用 `Direction.getNearest(worldPosition - factoryPos)`（工厂→拓展方向）检查工厂面向拓展的面，方向是对的——本次修复与之一致。

**修复**：三处 `SHAFT_BY_FACE.get(d)` / `get(startDir)` → `get(d.getOpposite())` / `get(startDir.getOpposite())`。
**构建通过**（0.2.33，IDEA MCP build 14s）。
**待用户复测**：漏斗放在 io_extension **非轴向四面**（轴向两端是应力接口面，设计上不提供 IO）应能取出工厂产物。

## 2026-08-20：三扫描防刷兜底规则重定义（需求确认版，待实现 0.2.24）

### 背景
用户重新定义了三扫描的用途：**三扫描是防玩家欺骗评估的兜底手段**。S0 初次扫描的真正作用是**过滤中间产物**（此前理解有误）。实测发现评估结束统计了大量中间产物（被当成产物）。

### 需求确认（经两轮追问，用户逐条确认）
- **扫描时机**：S0 在 **IO 激活前**扫描（房间未开工初始态）；S1=预热结束基线；S2=评估结束（IO 已停）终态。
- **产物**：key ∈ **输出方块实际 trace 收集到的种类**（`series.outputTotal>0` 的物品/流体集合，**不是配置的过滤白名单**）且净变化 > 0 → 输出。数量 = `net=(S2-S1)+O-I`。
- **中间产物**：key ∉ 输出种类，且 S0 无、S1 有、**且无 IO 输入流量（`ioIn==0`）** → **完全忽略**（即使被下游机器消耗也不计输入）。**⚠️ 0.2.24 实机 bug（已修复）**：最初未加 `ioIn==0` 条件，导致经 IO 输入的原料（圆石）在预热期积压到 S1 容器后，被误判为中间产物而忽略 → 工厂凭空产出安山合金。修复：中间产物判定必须排除有 IO 输入流量的外部原料。
- **消耗**：非中间产物的 key，`S1-S2` 净减少 → 输入（如煤 S1=40→S2=10 → 输入 30；预热期 S0→S1 烧的 10 不计）。
- **边界 1-A**：S0 有该物品（非输出种类）→ 不算中间产物，整体按初始库存处理。
- **边界 2-A**：输出种类物品净减少也按消耗处理（减少=消耗对输出种类同样适用）。
- **边界 3-B**：S0 全空判定需**物品+流体+能量全空**才触发简化路径。
- **S0 全空简化**：全空 → 完全不用 S1/S2 容器对比，工厂输入=IO 输入 trace、输出=IO 输出 trace。
- **防复制陷阱**：流体必须纳入全空判定——匠魂金属溶液预存储液罐，若只看物品，抽到输出方块即凭空复制新流体。
- **影响范围**：RATE（`auditRates`）+ REPLAY（`netBalance`）都按此规则改。

### 关键实现点
- S0 扫描前移到 `activateIoBlocks` 之前。
- "输出种类集合"从 trace 的 `series.outputTotal > 0` 提取（实际收集到的，非配置白名单）。
- 中间产物判定：非输出种类 且 S0 无该 key 且 S1 有 → 完全忽略。

## 2026-08-20：IO 平衡三扫描 + POI 复制（0.2.20-0.2.23）

### IO 平衡三扫描重写（用户定义标准）
- 公式：`net = (S2-S1) + IO输出 - IO输入`；net>0 输出、net<0 输入、net=0 无。
  **S1=预热结束基线（warmup），S2=评估结束终态（IO 已停）**；S0 仅无预热时回退、仅调试日志。
- 用户明示规则：IO 方块输入/输出自统计永远正确，不参与扫描修正；扫描只针对房间内原有容器（含掉落物、传送带）；S1 vs S2 增加→产出、减少→消耗。
- **0.2.21 重大错误修复**：旧 `auditRates` 的"消耗物归入输入"循环实际把消耗物写进**输出速率表**（`adjusted.put`，adjusted 作为 outputRates 返回）→ 消耗物同时出现在 input/output（用户 NBT 见 `output_item_rates` 含 `diamond_block:0.1`）。根因：0.2.20 把 RATE 基线从 S0 改成 S1 后，预热期带上积压进入基线 → 触发该循环。修复：`auditRates` 重写为纯三扫描净平衡（返回 `RateAudit(inputs, outputs)`），对"基线∪终态∪trace"每个 key 算 net，速率=net/评估tick；`EvaluationVerdict.rateResult` 改用其结果，删除废弃拟合代码。用户实测**符合预期**后移交 git。
- REPLAY 路径（`EvaluationReplay.netBalance`）0.2.20 已是同公式单循环互斥归属，结构上无此 bug（已核对，无需再改）。

### POI 复制参与评估（用户下一阶段计划：之前只是暂时禁用）
- 0.2.22 解除 Phase 4/5 的 POI 拒绝：`inspectPoiRecord` 从"非空即拒绝"改为"校验格式+返回"，`inspectBlockPalette` 移除 `PoiTypes.hasPoi` 拒绝。
- 复制链路（参照实体）：源读 POI → `RuntimeState.sourcePoi` → 发布窗口 `writePoi(target,pos,poi)`（`{Position,Sections,DataVersion}`）→ `tickTargetVerify` 校验 `Sections` 与写入一致。
- **0.2.23 格式 bug 修复（用户实机发现）**：`inspectPoiRecord` 校验 `pos` 用 `Tag.TAG_LONG` 导致真实记录全部报"格式无效"（回滚）。反编译 MC 21.1.219 merged jar 确认：`PoiRecord` 的 `pos` 经 `BlockPos.CODEC = Codec.INT_STREAM.comapFlatMap` 序列化为 **IntArrayTag（`[I;x,y,z]`，TAG_INT_ARRAY=11）**，非 LongTag → 改 `TAG_INT_ARRAY`。
- POI 记录自包含（位置+类型+票数，无实体 UUID），搬运后 eval_world 村民（Phase 5 已复制）可认领。**待用户实机复测：POI 方块+村民房间评估成功、副本 POI 可认领。**
