## 2026-09-29（续5）：0.4.4 —— 手持物品机壳改为**展示形态**（并否定一条"ENCASED 默认值"的猜测）

- **实机反馈**：用户要求手持呈现**展示形态**（3px 底座 + 四角立柱 + 顶部横梁 + 四面玻璃）且里面能看到微缩；当时物品显示的是"包壳那套/传统外壳"。
- **根因（用代码证据否定了转来的判断）**：机壳模型**不由方块状态决定**，与 `FactoryBlock.registerDefaultState` 里 `ENCASED=true` **无关**。证据链：
  1. `assets/createcmpor/models/item/factory_block.json` 是**显式**物品模型（原为 `{"parent": "createcmpor:block/factory_block_closed"}`）；`ModelBakery.loadItemModelAndDependencies` 把它注册成 `createcmpor:factory_block#inventory`，这条路径**不读 blockstate、不构造任何 BlockState**；
  2. `factory_block_closed.json` 是独立模型文件（30 个 element、只用 `#casing`、无玻璃），**不是** blockstate 里 `encased=true` 那套 multipart（`factory_casing` + panel/fill 共 14 条 selector）；
  3. multipart（`MultiPartBakedModel`）只由 blockstate 产生，物品路径根本拿不到它 ⇒ "物品用了 ENCASED 默认值 true 的外壳"不成立。
  （附带事实：`ENCASED` 默认 true 确实存在，用途是旧存档缺属性时落回传统模式——那影响的是**方块**，物品不受影响。）
- **改动**：
  1. **`models/item/factory_block.json` 的 parent 改为 `createcmpor:block/factory_display`**（展示形态，`render_type: cutout`，17 个 element：底座压边 + 3px 底座板 + 四角立柱 2×2px + 顶部横梁 + 四面 `minecraft:block/glass` 玻璃）。选"改物品模型 JSON"而不是"运行时构造展示态 BlockState 再取 block 模型"的理由：物品路径本来就不经过 blockstate，改 JSON 一行即可，且 GUI/手持/掉落物/展示框/JEI/配方预览**全部一致**；运行时取 block 模型拿到的是 multipart 包装，`renderModelLists`（传 state=null）会返回空，必须自己写状态感知的取四边形循环，代码多、风险大，还会与 JEI 显示不一致。
  2. **绘制顺序改为"先预览、后机壳"**：与世界里的顺序一致（不透明/实体 pass → 半透明覆盖），保证"隔着玻璃看里面"的合成关系与方块侧相同。
  3. `drawShell` 增一条**换模型时打一次**的 debug（模型类名 + 图层），排查"外壳用错模型"时直接给答案。
- **可见性几何核算（数值，非观感）**：预览盒 11px 居中 → x/z 落在 2.5~13.5px；`factory_display` 的四角立柱占 0~2 与 14~16 ⇒ **互不重叠**（两侧各余 0.5px）；顶部横梁在 y 15~16、预览顶在 14 ⇒ 不重叠；玻璃是 `cutout`，alpha=0 像素被丢弃 ⇒ 微缩不会被玻璃挡黑。底座上表面恰在 y=3px = `PreviewRender.BOTTOM_PX`，与世界里一致 ✓（**未改** `PreviewRender` 任何尺寸）。
- **构建**：标准命令 `./gradlew.bat build --console=plain` **被用户正在运行的游戏卡住**（非代码问题）：
  `build\moddev\artifacts\neoforge-21.1.235.jar is locked by: 22016 [Minecraft server] / 31276 [Minecraft NeoForge* 1.21.1 - 多人游戏（局域网）]` → `java.nio.file.AccessDeniedException: neoforge-21.1.235.jar.tmp -> neoforge-21.1.235.jar`。
  触发原因：IDEA runClient 那次构建更新了 `build/tmp/createMinecraftArtifacts/nfrt_artifact_manifest.properties`，导致 `:createMinecraftArtifacts` 不再 up-to-date（`artifactManifestEntries`/`artifacts` 输入变了），必须重写那个 jar，而它正被游戏占用。
  **绕过验证**：`./gradlew.bat build --console=plain -x createMinecraftArtifacts` → **BUILD SUCCESSFUL**（compileJava/jar/processResources 实跑，产出 `build/libs/createcmpor-0.4.4.jar`，其 `META-INF/neoforge.mods.toml` version=0.4.4、jar 内物品模型 JSON 已是 `factory_display`）。**关掉游戏后需再跑一次标准命令**（会重跑一次 NeoForm，约 1~2 分钟）。
- **未验证**：本次仍是**静态核实，未实机看观感**——玻璃四面是否真的"看得见里面"（cutout 的 alpha 丢弃语义 + GUI 图集 mipmap，理论上透明，但要人眼确认）；玻璃边框贴图是否压住微缩边缘 ~0.5px；`factory_block_closed.json` 现已无引用（保留未删，怕别处/后续要用）。

## 2026-09-29（续4）：0.4.3 —— **修复** P8 手持/物品栏预览"跑出方块" + 复核改进

- **实机现象（用户截图）**：世界里（BER 路径）预览位置/尺寸都正确；**手持与物品栏（BEWLR 路径）里预览被整体推出方块**，表现为一点机械结构飘在方块**左上方**、只露出局部；机壳本身正常。
- **根因（已定位到行，非试错）**：0.4.2 那行 `ms.translate(0.5F, 0.5F, 0.5F)` 是错的（它抄自报告 §3.3 P2，而报告那条结论本身有误）。
  - `ItemRenderer.render:123-124` 施加 display 变换 `M_ctx` 后再 `translate(-0.5,-0.5,-0.5)`，然后才调 `renderByItem`；`T(-0.5)` 的作用只是把 0..1 的方块模型搬到"以物品原点为中心"（-0.5..0.5），**坐标系并没有换**——在这一层，坐标 `c∈[0,1]³` 仍然是"方块最小角为原点、1 单位 = 1 格"的方块模型空间，与 BER 里 `FactoryPreviewRenderer` 所处空间逐位同构。
  - 再加 `+0.5` 等于把画的东西整体平移半格：GUI 里 = 0.5 格 × 16 px/格 × 0.625(display scale) = **5 屏幕像素**，而整个机壳只有 10 px、预览只有 6.9 px ⇒ 预览几乎全部落在方块外（正是截图里的"左上方一小点"）。
  - **Create 为什么用 `+0.5`（`CustomRenderedItemModelRenderer:24-25`）**：那是把坐标系换成"以方块中心为原点"的**居中空间**，所以它的 `PartialItemModelRenderer.render:64-65` 画模型四边形时要再 `translate(-0.5)` 抵消回来。我们要的是"最小角为原点"的模型空间，两者恰好差半格——**报告把两种约定混为一谈了**。
  - **不依赖推理的判据**：本类在同一层先画的机壳（`drawShell`，同样 0..1 空间、同样入口姿态、零额外变换）实机位置正确 ⇒ 入口姿态就是预览需要的那个空间。另核实 `drawShell` 全程不碰姿态栈（`renderModelLists`/`renderQuadList` 只读 `poseStack.last()`），不存在"残留学变换"。
- **修复**：删掉那行 translate（预览与机壳画在同一层），其余一行未改（`PreviewRender` 的缩放/居中/底部对齐数学原样复用，方块侧完全不受影响）。
- **顺带折入对抗性复核的改进**（复核结论：无 CRITICAL/HIGH；机壳自画路径与原版四边形分支等价；注册/线程均核实通过）：
  1. **[中] `PreviewBakeCache.ITEM_RESOLVED` 值改存内容指纹**（不再是 `PreviewBaked`）：原先"上限 512 的身份表"会各自持有重顶点缓冲，把 LRU(32) 的持有效果放大 16 倍（最坏上百 MB）；现在重对象唯一持有者是 LRU。指纹被 LRU 淘汰时条目作废、当帧重新解析。
  2. **[低] 新增 `PreviewBakeCache.ensureLevel(level)`**：退出/切换世界（含切维度）时整体清空——报告 §4.5 要求的清理时机，0.4.2 漏了（只有资源重载监听在清，而类注释却写着"退出世界时调用"）。
  3. **[低] 烘焙预算改用 `AnimationTickHolder.getTicks(true)`**（含暂停期间推进的 tick），避免暂停界面把"每 tick 一份"退化成"整个暂停期只烘一份"（容器界面本就不暂停，属极端情况兜底）。
  4. **[提示] `ModifyBakingResult` 加幂等护栏**（已是包装模型就跳过）；`drawShell` 拆包装改**逐层**（最多 4 层），防别的模组也换同一模型时把机壳拆丢。
  5. 复核指出的 javadoc 行号笔误（`BakedModelWrapper:84-87`→`85-88`）已改。
- **构建**：`./gradlew.bat build --console=plain` → **BUILD SUCCESSFUL**（0.4.3；`mod_version` 0.4.2→0.4.3）。
- **仍未验证**：0.4.3 **未经实机复测**（本次改动是"删一行"，但需用户确认三个上下文：物品栏/第一人称/掉落物）；GUI 里预览约 6.9 屏幕像素是否"看得清"仍是观感问题（若嫌小，只能给 GUI 单独放大 `BOX_PX`，但那会让预览相对机壳变大、可能穿插，**需用户定夺，未擅自改**）；物品侧无 LOD 的帧时、资源重载回归仍未跑。

## 2026-09-29（续3）：0.4.2 —— P8 手持/物品栏里的工厂物品显示自带微缩预览

- **目标**：手持（第一/第三人称）、物品栏 GUI、掉落物、展示框里的工厂物品，显示它**自己携带**的那份微缩预览。落地依据是子代理调研报告 `%TEMP%\cpe-src\HELD-ITEM-REPORT.md`（javap + 源码实测，含 11 条坑位按危险度排序）。
- **路线（为何不用 `"parent": "builtin/entity"`）**：走 `ModelEvent.ModifyBakingResult` 换物品 BakedModel。`builtin/entity` 能跑通但：① `BuiltInModel.getQuads()` 返回空列表 → 一旦降级就是**物品完全隐形**；② 丢掉 `block/block` 的整套 display 变换（GUI/手持/掉落物的角度与缩放要手抄）；③ `gui_light`/`isGui3d` 语义要自己对。换模型这条路 display 变换天然继承（物品模型 `factory_block_closed.json` 的 `parent: block/block`），`getQuads` 仍转发原模型 → JEI/合成预览/粒子图标等旁路取用行为不变。
- **新增类（3 个，均在 `com.yansunsky.createcmpor.client`）**：
  - `FactoryPreviewItemModel extends BakedModelWrapper<BakedModel>`：覆写 `isCustomRenderer()→true`，以及 **`applyTransform()`：`super` 施加变换副作用后 `return this`**。后者是硬坑——`BakedModelWrapper.applyTransform` 默认 `return originalModel.applyTransform(...)`，不覆写就**永不调用 renderByItem 且零报错**（Create `CustomRenderedItemModel` 注释与 NeoForge `BakedModelWrapper` 源码双证）。
  - `FactoryItemRenderer extends BlockEntityWithoutLevelRenderer`（构造 `super(null,null)`，同 Create 的 `CustomRenderedItemModelRenderer`）：6 参 `renderByItem`。先画机壳（逐行复刻 `ItemRenderer.render` 的 `flag1=true` 原版四边形分支：`getRenderPasses` → `getRenderTypes` → 公开的 `renderModelLists` + `getFoilBufferDirect`），再 `translate(0.5,0.5,0.5)` 抵消 `ItemRenderer` 的 `translate(-0.5,-0.5,-0.5)` 回到 0..1 方块空间，把绘制交给方块侧同款的 `PreviewRender`（缩放/居中/底部对齐数学**一行没改**，逐行复用）。
  - `FactoryItemClientExtensions implements IClientItemExtensions`：单例持有并返回上面那个 BEWLR（每次绘制都会问，不能每次 new）。
- **注册点（`client/ClientSetup.java`，三个 MOD 总线 handler）**：与既有 `RegisterRenderers` 同段 post（源码 `ClientHooks.initClientHooks`），且既有 `已注册 ShaftRenderer BER 兜底` 日志在 `run/logs/debug.log` 有实机证据 → 本类确实收到 MOD 总线事件。
  - `ModelEvent.ModifyBakingResult`：把 `ModelResourceLocation.inventory(createcmpor:factory_block)`（= `#inventory`）替换为包装模型。键格式**双向源码核实**：`ModelBakery:176` 用它注册物品模型、`ItemRenderer` 构造器 `:78` 用同一式子登记 shaper；键不存在时只记 debug 并保持原样（安全失败＝退回 0.4.1 外观）。
  - `RegisterClientExtensionsEvent#registerItem`：**只注册自己那一个物品**（重复注册是启动期 `IllegalStateException`，不是覆盖）。
  - `RegisterClientReloadListenersEvent`：清方块侧与物品侧缓存（原先 `FactoryPreviewRenderer.clear()` 无任何调用方）。
- **缓存（改造 `PreviewBakeCache`）**：物品侧三级——① `IdentityHashMap<CustomData, PreviewBaked>` **身份快路径**：组件不可变 ⇒ 组件没变时 `stack.get(BLOCK_ENTITY_DATA)` 返回同一实例，每帧 O(1) 命中、**连 NBT 都不解析**（必须做：1.21.1 无 `ItemStackRenderState`，每帧每槽位都会调 `renderByItem`，而 `PreviewSnapshot.load` 要走调色板的 `BlockStateParser`）；上限 512，超限整体丢弃。② 内容指纹 `PreviewBaked.contentHash(snapshot)` 的 LRU(32)。③ 失败集（上限 32）。**light 仍不进任何缓存键**（渲染期 `.light(packedLight)`）⇒ 手持移动的光照变化不触发重烘。另加**每客户端 tick 最多新烘一份**的预算：开物品栏瞬间几十个工厂物品不会同时烘，未中签的槽位这一帧只画机壳、下一 tick 补（观感逐个亮起）。
- **降级矩阵（全部静默：只画机壳，不画预览）**：无 `BLOCK_ENTITY_DATA` / 组件空 / 无 `preview` 子标签 / `PreviewSnapshot.load` 返回 null（版本不符、脏数据）/ `nonAirCount()==0` / **`Minecraft.getInstance().level == null`**（主菜单、资源包界面、退世界瞬间——此时**连快照都不解析**，因为 `VirtualRenderWorld` 构造第一条指令就解引用 level）/ 烘焙返回 null / 新配置 `preview.enableFactoryItemPreview=false`（默认 true，0.4.2 新增）。
- **规避"GUI 崩溃"**：`renderByItem` 全体 `try/catch(Throwable)`（GUI 路径抛异常 = `GuiGraphics:1298-1306` 的 `CrashReport("Rendering item")` → `ReportedException`，**直接崩游戏**）；姿态 push/pop 一律 `try/finally` 配平；日志只走 debug，不刷屏。
- **规避"无限递归"**：降级与机壳路径**只画四边形**（`ItemRenderer.renderModelLists`），**绝不调用** `BlockRenderDispatcher.renderSingleBlock` 与 `ItemRenderer.render`。递归真身：`renderSingleBlock` 对 `RenderShape.ENTITYBLOCK_ANIMATED` 方块用"零组件空壳 stack + `ItemDisplayContext.NONE`"反向回调 `renderByItem`（`BlockRenderDispatcher:159-161`）；本方块 `getRenderShape` 是 `MODEL`，另有硬护栏——`getModel` 拿到的模型若 `isCustomRenderer()` 为真且不是自己的包装，直接 return。
- **构建**：`./gradlew.bat build --console=plain` → **BUILD SUCCESSFUL**（0.4.2；`mod_version` 0.4.1→0.4.2）。
- **未验证（如实标注，禁止当结论）**：
  1. **未实机验证**：全部结论来自 javap/源码静态核实，本会话**没有启动过游戏**。GUI 里微缩内容的实际观感（报告坑 12：GUI 下只有 ~7.5 屏幕像素，可能"看不清"；是否给 GUI 上下文放大 `BOX_PX` 属调参）**未经人眼确认**。

### 背景：为什么一开始以为是设计取舍

**"能不能正确显示连接纹理？"** —— 实机对照：**Create 自己的蓝图全息图显示 CTM 完全正常**，说明正确路线存在。已定位关键差异（源码证据 `ConnectivityHandler.java:384`）：

```java
public static boolean isConnected(BlockGetter level, BlockPos pos, BlockPos other) {
    T one = checked(level.getBlockEntity(pos));
    T two = checked(level.getBlockEntity(other));
    if (one == null || two == null) return false;
    return one.getController().equals(two.getController());   // 需要多方块控制器状态
}
```

- 连通纹理判定**依赖 BE 的多方块控制器状态**（`ItemVaultCTBehaviour.connectsTo` → `ConnectivityHandler.isConnected`）；
- Create 的 `SchematicLevel` 里有**从蓝图 NBT 还原的真实 BE**（带控制器数据）→ 所以它画得对；
- **我们的快照只存方块状态、刻意不存 BE NBT**，代理 BE 是空壳 → 连通判定必然退化 → CT 索引进而错到黑色区域。

- B 快照额外携带多方块连接信息（控制器坐标/连接位），换取正确 CTM——NBT 体积与采集复杂度上升，收益仅在高倍放大审视时可见。

### 缺陷 A（真 bug）：回滚原因在异步路径上被丢弃

## 2026-09-22：评估期日志降噪（克隆进度，未提交）

1. 初版用 `(processed/step != (processed-1)/step)` 跨界判定 → **降噪不足**（16 区块仍 18 行）：因为 verified 与 published 交替上升会反复跨同一 step。

## 2026-09-22：打包机 IO 兼容 + 输出容量随速率 + 冻结卡死豁免（0.3.48，已提交 7670778，实测通过）

**起点**：玩家反馈"io 输出输入效率过慢"，且"输出打包一次最多 4 组，输入拆包却能进 9 组"；随后自测又发现"冻结异常"（源房间卸载超时回滚）。

### ① 打包机兼容：物品槽改「多分片」（FactoryBlockEntity.ItemHandler）

**Create 拆包源码确证**（`DefaultUnpackingHandler.unpack`，6.0.10）：
- `for slot: itemInSlot = getStackInSlot(slot)`
  - **空槽分支**：`maxStackSize = getSlotLimit(slot)`，且 **忽略 `insertItem` 的返回值**直接认定"全放下了"；
  - **非空槽分支**：`slotLimit = min(itemInSlot.getMaxStackSize(), getSlotLimit(slot))` —— **恒 ≤ 物品堆叠上限**。
- 一包上限 `PackageItem.SLOTS=9` × 64 = **576 个**；每签名只有 1 槽时一次只能吃 64 → **整包拆包失败**。

**修复**：每签名按容量推导分片数 `ceil(capacity/64)`（上限 9，= 打包机一包上限），分片 i 覆盖 `[i×64, (i+1)×64)`：
- `getStackInSlot(shard)` = 该片占用量（空片返回 EMPTY → 走"空槽分支"）；
- **`getSlotLimit(shard)` = 该片剩余空间**（不是总容量！否则空槽分支会超领、真实插入不足的差额被**凭空销毁**）；
- `insertItem` 只接受本片余量；`extractItem` 从输出区扣减；`isItemValid` 仅输入区且必须匹配该片容器物品；
- **末片兜底**：容量 > 576 时最后一片覆盖剩余全部容量 → 保证存量**全覆盖、可取尽**（否则超出部分永久卡死）；
- 内部仍是单一 `Container.amount`（long），**存档格式不变**。

**逻辑自测（31/31 通过，本地脚本模拟 Create 语义）**：取尽性（64/256/576/1280/4096/132020）、拆包认领=实入无超领、装箱含 while 重试取满整包、越界/负索引/simulate 无副作用、满仓拒收背压、容量随速率。
- **中途澄清**：绝对偏移分片会导致「单轮吞吐腰斩」（容量 576 单轮只出 320，因取走后总量下移）；但打包机内层有 `while(continuePacking)` **重试遍历**（实测 9 轮取满整包），**不依赖单轮取完**，故无需改 per-shard 记账（那会改 NBT 格式）。

### ② 输出容量随速率放大（同文件）

**根因**：`ITEM_OUTPUT_BUFFER=256` 是**硬编码**，与速率无关 → ① 6601 个/秒的产线只有 **0.04 秒缓冲**，产物持续溢出被静默丢弃；② 容量 256 → 分片只有 `ceil(256/64)=4` → 打包机一包只能取 4 组（与玩家观察完全吻合）。

**修复**：RATE 输出容量改为 `max(保底 256/4000, capacityFromTickRate(rate))` = **速率 × 20 秒**，与输入侧同口径。REPLAY 侧原本已是 `max(保底, 峰值×20)` 无需改。效果：速率 ≥28.8/秒 → 容量 ≥576 → 分片 9 → **一包取满 9 组**。

### ③ 冻结异常：vanilla 卸载收尾卡死（0.3.41 探针立功）

**日志实测诊断**（`run/logs/latest.log`）：
```
dim=compactmachines:compact_world, players=0, roomChunks=1
  [128, -256] idle=false {visible=false, updating=false, pendingUnload=true, chunkNow=false, entities=false} tickets=[]
```
**关键：`tickets=[]`（无任何票据）** → 推翻"被外部模组强加载"的假设；内容确已卸载，却卡在 **`pendingUnloads`**。

**根因（vanilla ChunkMap 源码确证）**：`scheduleUnload` 是**异步自我重试**——
```java
if (!holder.isReadyForSaving()) scheduleUnload(pos, holder);  // 无限重试
else pendingUnloads.remove(pos, holder);                      // 唯一出口
// isReadyForSaving() = getGenerationRefCount()==0 && saveSync.isDone()
```
该 holder 的 `saveSync`（`addSaveDependency(fullChunkFuture/tickingChunkFuture/entityTickingChunkFuture)` 串接）永不归零 → 永远留在 `pendingUnloads` → 我们判非 idle → 200 tick 超时回滚。**这解释了"单机也 100% 复现"与"自动卸载不生效"**（卸载发起了但永不完成），且与外部模组无关。

**修复 A（文案）**：新增 `EvaluationStorageBridge.describeUnloadBlocker`，按实际子条件归类（有票据 / 内容在内存 / 实体未卸 / **卡在 pendingUnloads**），替代旧文案"持续被外部票据加载"（与 `tickets=[]` 矛盾，误导排查方向）。

**修复 B1（开关）**：新增 `Config.UNLOAD_STUCK_PENDING_TICKS`（默认 **0=严格不变**；>0 时启用豁免）。放行条件（**逐区块**，不可写成"全部内容已卸 + 任一卡死"——那会误放行「1 卡死 + 1 被外部强加载」，实测自测抓到此缺陷并修正）：
- 每个区块满足「严格 idle」**或**「卡死的 pendingUnloads（内容已卸 + 无票据）」；
- 连续 N tick 满足 → 放行冻结，打 WARN 诊断 + 玩家提示（lang `frozen_after_stuck_unload`）。

**日志增强**：新增 `isChunkContentUnloaded` / `isUnloadStuckOnPending` / `hasUnloadStuckChunk` / `areChunksIdleOrStuckPending` / `describeUnloadBlocker`，后续同类问题可直接定位到具体子条件。

**验证**：`build -x test --offline` 通过（0.3.48 jar，jar 内版本已核对）；A+B1 逻辑自测 **14/14 通过**（严格模式不变、豁免计时准确、混合场景逐区块判定、判定函数纯度）；**用户实机测试通过**。

**用户需知**：`unloadStuckPendingTicks` 默认 0（严格）。遇到"卡在 pendingUnloads"的报错时，设为 100 左右即可放行（区块内容已卸载、读盘评估安全）。

## 2026-09-22：多应力输入方块刷应力漏洞修复（未提交）

**玩家反馈**：只要房间里有**两个应力输入方块**，就能做出"无限应力输出机"——固化后工厂 tooltip 显示 `应力：输入 0.0 SU / 输出 3710976.0 SU`（`应力量 3,339,878.25 SU`，RATE），而空间内并无任何真实应力源。

**根因（Create 源码确证）**：
- `StressEvaluationRegistry.consume()` 扣除"评估期注入的虚拟容量"时**只扣一份**：旧代码对同网络 INPUT 采样取 `stableValue`（中位值）后只赋值一次 `totalVirtual = stableValue(inputSamples, …)`。
- 而 Create `KineticNetwork.calculateCapacity()` 是**对所有 source 求和**（`presentCapacity += getActualCapacityOf(be)`；`getActualCapacityOf` = `sources.get(be) × |be.getGeneratedSpeed()|`，见 KineticNetwork.java:133-147、165-175）。
- 同网络挂 N 个 `stress_input` 时：`capacity = N × 16384 × |speed|`（+真实容量），只扣 `1 × 16384 × |speed|` → `net = (N−1) × 16384 × |speed| − stress`，N≥2 即凭空判为"应力输出"。
- **数值印证截图**：`3710976 = 1 × 16384 × 226.5`，正是 `(N−1)×16384×speed`（N=2、转速 226.5）。

**修复（StressEvaluationRegistry.java）**：
1. `totalVirtual` 改为**按 IO 方块分组、每组取稳定值后求和**（遍历 `perIo`，只统计 networkId 相同且 type=INPUT 的序列）→ N 份虚拟容量全额扣除。修复后该场景 net=0 → `StressProfile.EMPTY`，工厂不再凭空提供应力。
2. `realCapacity = max(0, sCap − Σvirtual)`；另加相对阈值 `epsilon = max(1, |sCap|×1e-6)` 抹掉浮点残差造成的假输出/假输入。
3. **护栏告警**：同网络 `inputBlockCount > 1` 时打 WARN（网络 id、输入方块数、Σvirtual、net），便于线上发现新堆叠变种；只告警不拒绝。
4. 类与 `consume()` javadoc 同步为 `net = (capacity − Σvirtual) − stress`，写明漏扣即凭空产出。

**影响面核查**：并行分支共用 `consume()`（key=`parallelTraceKey`）→ 自动覆盖；不同网络各 1 个输入 → 不产生假输出；单输入房间 → 与旧实现等价（无回归）；真实应力源仍是合法净输出。

**验证**：`compileJava`、`build -x test --offline` 通过；`StressEvaluationRegistry` 是唯一改动文件（未提交）。

**待实机回归**：① 漏洞场景（2 个输入方块）固化后应力应为 `输入 0 / 输出 0` 且服务端出现多头 WARN；② 单输入驱动真实耗能机械仍得 `inputSU>0`；③ 空间内真实应力源仍得 `outputSU>0`；④ 单输入+输出直通仍 net=0。

**用户报告**：「评估完之后重置回去直接凭空生成产物了，评估开始前里面确认过没东西的」。

**根因（逐条源码证实）**：`sophisticatedcore:storage_uuid` 只是一个**指向全局 SavedData 的 UUID 指针**：

- 背包 ItemStack 上只有该 DataComponent（UUID 类型）；真实内容在**主世界全局 SavedData**
  `BackpackStorage.backpackContents`（`Map<UUID, CompoundTag>`）。
- `BackpackStorage.get()` 经 `ServerLifecycleHooks.getCurrentServer()` → **主世界** `DimensionDataStorage`，
  **不按维度隔离**——任何维度拿到的都是同一个 Map。
- 克隆管线**逐字节复制区块 NBT**（`staging.write(sourceChunk.tag().copy())`），`storage_uuid` **一字不改**
  → 副本背包与源房间背包**共用同一 UUID、同一份物理内容**：

```
源房间背包 ItemStack ──storage_uuid = U──► BackpackStorage（主世界全局 SavedData）
                                                    ▲
eval_world 克隆背包 ──storage_uuid = U（原样复制）──┘   同一份内容
```

评估期副本侧任何写入（机器产物送入背包、**磁铁升级吸取副本地板掉落物**——用户截图正好挂着高级磁铁）
都直接落到源房间那个背包 → 表现为"还原回去凭空多出产物"。**三扫描完全看不见**：S0/S1/S2 读的是同一个
全局 store，自洽且守恒，只能发现"副本消耗了背包内容"，无法发现跨世界串写。

**旁证**：全仓从未调用过 SBP 写入/隔离 API（`setBackpackContents`/`removeBackpackContents`/`cloneBackpack`/

## 2026-08-28：多分支并发评估架构调研（未修改代码）

**源码核实**：当前实现的 `EvaluationSavedData` / `EvaluationSession` / `EvaluationManifest` / `EvaluationTrace` 均按会话 UUID 或 roomCode 保存；每个会话有独立 staging 路径、manifest、实体重写状态和 scheduler state。但 `eval_world` 是单一维度，manifest 当前把目标坐标设为源 room 的同坐标；`EvaluationCloneManager.publishingSession` 又把正式目标发布串行化。

**关键隔离结论**：同坐标多会话只有在源房间 chunk 集不重叠时才成立；CM 的 `GraphChunkManager` 以单一 `ChunkPos -> RoomChunkNode` 映射反查 compact_world 房间，因此源房间本身依赖坐标隔离。eval_world 没有 CM 房间注册/反查语义，且 scheduler、审计、IO 激活按 `RoomInstance` AABB 扫描。若使用空间偏移，必须为每个会话保存目标原点/变换，并把所有 AABB、BlockPos、实体位置、铁路节点和清理逻辑改为目标坐标；不能只改 manifest chunk 坐标。

**并发风险**：`EvaluationTrace.Hub` 和 `StressEvaluationRegistry` 以 roomCode 为 key，理论上不同房间可并行；同一 roomCode 不能并行。目标 chunk 的 region/entity/POI 存储是 eval_world 共享 worker，当前目标冲突检查和写入/删除假定目标坐标专属；多个不重叠 footprint 可并行，但文件 worker、ChunkMap ticket、forced chunk、实体加载仍共享维度资源。

**铁路/实体风险**：Create `GlobalRailwayManager` 的 trains、trackNetworks、signal groups 是全局 SavedData，不按维度拆分；当前复制靠新 UUID、维度 palette 和“图节点全在 room bounds”扫描。`EvaluationRailwayTransfer` 的 `findGraph`/cleanup 只按 eval_world + AABB 过滤，空间偏移必须同步改变 bounds，否则会找不到或误删别的会话图。已有验收记录明确列出铁路副本渲染/碰撞/拆卸及时刻表隔离风险，属于需实验验证的未解决风险。

**方案结论（供后续决策）**：在不创建多个 CM 房间的前提下，单一 eval_world + 每会话空间偏移可实现真正并行，但改动面和实体/铁路风险最大；多个维度隔离更强但需要动态维度生命周期和同样的坐标变换，且 Create 全局铁路管理器并不会自动按维度隔离；多个 CM 房间隔离复用 CM 但违背约束并增加房间注册/生命周期成本；顺序基线改动最少且风险最低，但无并发吞吐。当前源码最支持的演进路径是保留单一 eval_world，先限制为不重叠的“同坐标、会话独占 footprint”并发；若必须同一源房间多分支并发，再引入显式目标原点/坐标变换，并先禁用或单独串行化铁路/跨实体内容，完成碰撞、UUID、轨道图和清理实验后再开放。

## 2026-08-20：三扫描防刷兜底规则重定义（需求确认版，待实现 0.2.24）

### 背景
用户重新定义了三扫描的用途：**三扫描是防玩家欺骗评估的兜底手段**。S0 初次扫描的真正作用是**过滤中间产物**（此前理解有误）。实测发现评估结束统计了大量中间产物（被当成产物）。

### 需求确认（经两轮追问，用户逐条确认）
- **扫描时机**：S0 在 **IO 激活前**扫描（房间未开工初始态）；S1=预热结束基线；S2=评估结束（IO 已停）终态。
- **产物**：key ∈ **输出方块实际 trace 收集到的种类**（`series.outputTotal>0` 的物品/流体集合，**不是配置的过滤白名单**）且净变化 > 0 → 输出。数量 = `net=(S2-S1)+O-I`。
- **中间产物**：key ∉ 输出种类，且 S0 无、S1 有、**且无 IO 输入流量（`ioIn==0`）** → **完全忽略**（即使被下游机器消耗也不计输入）。**⚠️ 0.2.24 实机 bug（已修复）**：最初未加 `ioIn==0` 条件，导致经 IO 输入的原料（圆石）在预热期积压到 S1 容器后，被误判为中间产物而忽略 → 工厂凭空产出安山合金。修复：中间产物判定必须排除有 IO 输入流量的外部原料。
- **消耗**：非中间产物的 key，`S1-S2` 净减少 → 输入（如煤 S1=40→S2=10 → 输入 30；预热期 S0→S1 烧的 10 不计）。
- **边界 1-A**：S0 有该物品（非输出种类）→ 不算中间产物，整体按初始库存处理。
- **边界 2-A**：输出种类物品净减少也按消耗处理（减少=消耗对输出种类同样适用）。
- **边界 3-B**：S0 全空判定需**物品+流体+能量全空**才触发简化路径。
- **S0 全空简化**：全空 → 完全不用 S1/S2 容器对比，工厂输入=IO 输入 trace、输出=IO 输出 trace。
- **防复制陷阱**：流体必须纳入全空判定——匠魂金属溶液预存储液罐，若只看物品，抽到输出方块即凭空复制新流体。
- **影响范围**：RATE（`auditRates`）+ REPLAY（`netBalance`）都按此规则改。

### 关键实现点
- S0 扫描前移到 `activateIoBlocks` 之前。
- "输出种类集合"从 trace 的 `series.outputTotal > 0` 提取（实际收集到的，非配置白名单）。
- 中间产物判定：非输出种类 且 S0 无该 key 且 S1 有 → 完全忽略。
