# 43 · 评估工厂「微缩预览」可行性评估

### 1.3 渲染技法（反编译源码实测）

反编译：Vineflower 1.10.1（Gradle 缓存内），产物在临时目录 `%TEMP%\cpe-src`。

**核心类 `client/PrecisionSpaceRenderer`（699 行，实现 vanilla `BlockEntityRenderer<PrecisionSpaceBlockEntity>`）：**

1. 每个 BE 配一个 `VirtualMicroWorld`（`WeakHashMap<BE, VirtualMicroWorld>` 懒建）。
2. 微缩世界 = **Create 的 `VirtualRenderWorld` 子类**（PE 的 `NonVisualVirtualRenderWorld`，仅覆写 `supportsVisualization() → false` 以禁用 Flywheel 参与）。
3. 微缩方块状态**不在世界里**，而是存在 BE 的 `BlockState[343]` 数组里；渲染前把状态写进虚拟世界（`level.setBlock(pos, state, 2)`），并按需为 `EntityBlock` 造**代理 BE**（`newBlockEntity(pos,state)` + `setLevel(虚拟世界)` + `setBlockEntity`）。
4. **变换**：常量 `SCALE = 1/7 ≈ 0.14285715`；每格 `poseStack.translate(cellX*SCALE, cellY*SCALE, cellZ*SCALE); poseStack.scale(SCALE,SCALE,SCALE)` —— 即整个 7×7×7 网格正好铺满 16³ 方块体积（外壳模型 2px 厚，压在最外圈上）。
5. **静态方块**：`blockRenderer.getBlockModel(state)` → 逐 `RenderType` 调 `blockRenderer.renderBatched(...)`；异常时兜底 `renderSingleBlock(...)`；并逐格记录"这一格是否渲染失败"，失败后不再重试。
6. **光照**：`level.setExternalLight(packedLight)` / `resetExternalLight()` —— **这是 Create `VirtualRenderWorld` 自带的方法**（javap 已确认存在），把微缩方块统一吃宿主方块的光照。
7. **方块实体**：取 vanilla `BlockEntityRenderDispatcher.getRenderer(proxy)` 直接 `render(...)`；皮带（`BeltBlockEntity`）走自己的 `PrecisionBeltRenderer`（还额外画带上的物品）；双联箱子用固定光照的 `MultiBufferSource` 包装。
8. **运动件特判**：如果一个格子是 kinetic 方块且没有被上面的 BE 渲染覆盖，先试 `renderBareKinetic`（轴/齿轮直接用 `CachedBuffers.partialFacing*` + `AllPartialModels` 手动转会），再退到 `renderKineticPartials`（其余 Create 模型），转角按 `speed + gameTime + 坐标相位` 算，保证与外网一致。
9. **性能**：BE 维护稀疏的"占用格索引表"（`occupiedCount`/`occupiedIndices`），只遍历非空气格；每客户端 tick 对代理 BE 调 `SmartBlockEntity.tick()` 驱动 Create 的 render state 动画。

**其它渲染相关类**：`EngineeringPreviewRenderer`（幽灵预览）、`PrecisionBeltRenderer`、`ClientEvents`。

### 1.3b 逆向深挖补充（第二路 agent 报告，含关键坑）

1. **整个技法的"灵魂"只有一行**：那个虚拟世界子类必须覆写 `supportsVisualization() → false`。
   原因：Create 的 `VirtualRenderWorld implements flywheel VisualizationLevel`（默认 true），Flywheel 对任何该接口实例都返回"支持可视化" → Create 全部渲染器（`KineticBlockEntityRenderer.renderSafe` 第一行就是早退）直接跳过，而 Flywheel 又不管理这个伪 level → **微缩世界整块不渲染，且不报任何错**。关掉它才能逼 Create 走 legacy BER 路径。
2. **宿主方块是 `RenderShape.INVISIBLE`**（模型完全不参与普通方块渲染，全部交给 BER）。我们的底座/展示罩**不必**照抄——底座可以照常走 `RenderShape.MODEL`，只把微缩内容交给 BER。
3. **AO 来自虚拟世界内部邻接**（微缩方块会互相遮光，观感成立）；`VirtualRenderWorld.getShade()` 恒为 1 → 方向明暗被抹平（一种"平光"观感，可接受）。
4. **皮带必须自写渲染器**：Create 原生皮带渲染器用微坐标做视锥剔除与相机朝向 → 在 1/7 尺度下**完全错误**；PE 用 `宿主方块坐标 + 局部坐标×(1/7)` 反算真实世界位置重做 billboard。**这是我们 MVP 直接跳过皮带的硬理由**（要显示皮带就得额外写一套）。
5. **动画依赖手动驱动**：虚拟世界里的 BE 永远不被 tick，PE 每个 game tick 手动 `smart.tick()` 一遍来驱动 Create 的 render state；异常只 trace。→ 我们若做纯静态，**这条整段可以删掉**（更安全）。
6. **PE 自己的同步预算（可作我们的上限参照）**：增量包 ≤ 256 KiB/包、**单 BE NBT ≤ 128 KiB**、整份快照预算 ≤ 192 KiB，超限游标分片续传、单 BE 超限直接丢弃并告警。**注意：即使按这个"宽上限"，也远大于我们展示所需的 2~8 KB**，说明我们完全可以做得更保守。
7. **性能模型（PE 是反面教材）**：343 格**逐帧重新 tessellate，无几何缓存、无 LOD**。我们的内容静态，应该烘一次 + 距离早退（见 §3.3）。

### 1.4 Sable 到底用在哪

`grep -rl "ryanhcode.sable"` 的结果：**`block/*`、`blockentity/PrecisionSpaceBlockEntity`、`microspace/MicrospaceManager`、`interaction/SableRayTransform`、`debug/ServerSaveWatchdog`** ——即：

- **Sable 负责"物理后端"**：微缩空间被装配成 Sable 的 sub-level（真实 chunk 存在于某个 backend 区域），并提供应力/物品/流体/红石的跨边界桥接、方块射线拾取（micro 交互）等。
- **client 渲染包几乎不用 Sable**（只有 `PrecisionDebugOverlay` 引用）。

**对我们的意义**：我们只借"渲染"这一层，**完全不需要 Sable**。这点非常关键——Sable 是侵入性极强的库且许可为 PolyForm Shield（非 OSI），引入它会显著抬高兼容与法务成本。

## 2. 我们手上已有的能力（CreateCMPOR 现状实测）

### 2.1 数据侧：房间快照代码已存在（但零调用）

`compat/cm/RoomCloner.snapshot(ServerLevel, IRoomBoundaries)`（:21-42）已经在做我们要的事——实测**目前没有任何调用点**（只有同类里的 `compareSameCoordinates` 被 `/ccmpor` 调试命令用），属于可复用的现成骨架：

```
AABB inner = boundaries.innerBounds();
for (BlockPos absolute : BlockPos.betweenClosed(min, max-1))
    snapshot.addBlock(relativePos, level.getBlockState(absolute));   // (相对坐标, BlockState)
```

`RoomSnapshot` = `width/height/depth` + `List<BlockEntry(relativePos, BlockState)>` + `List<BlockEntityEntry(relativePos, CompoundTag)>`。

房间尺寸来源：`IRoomBoundaries.innerBounds()`（CM core-api 7.0.81 的 `IRoomBoundaries` 提供 `innerBounds()/outerBounds()/innerChunkPositions()` —— javap 确认）。CM 房间尺寸档位：tiny 3 / small 5 / normal 7 / large 9 / giant 11 / colossal 13 / soaryn 45（立方）。

**缺口**：现有 `RoomSnapshot` 是"全量列表 + 携带 BE NBT"，面向"复制房间"用途，**不适合直接塞进 BE 存档**（体积大、含 air、含完整 BE 数据）。展示用途需要一份**精简、带调色板/位图编码、有体积上限**的快照。

**关键约束：固化窗口是唯一机会。** 工厂 BE NBT 里**现在没有任何房间方块数据**（`write` 键表实测：只有速率/秒槽/容器/模板/应力档案/restore_state+restore_machine）。评估副本的 manifest 只存区块 hash；房间方块数据的临时载体只有三处，且都会在清理阶段消失：

- `EvaluationCloneManager.RuntimeState.sourceTags`（:295 / :1339，CLEANING 阶段 :991 释放）——**原始 chunk NBT**，`EvaluationStorageBridge.inspectBlockPalette`（:490）已经会解析它的区块 paletted container，可据此在不加载区块的前提下取方块
- eval_world 里的同坐标副本（已加载，可直接 `getBlockState`）
- `data/createcmpor/evaluation-staging/<sessionId>` 目录（:992 删除）

固化之后源房间已卸载，**不能再回源房间读方块**。所以"采集"必须挂在固化流程里（建议从 eval_world 副本读，因为它保证已加载且是评估终态）。

### 2.1b 「排除房间自带地板/墙体」几乎是免费的（CM 源码实测）

- `IRoomBoundaries.innerBounds()` 的默认实现就是 `outerBounds().deflate(1)`（CM core-api 源码）——**1 格厚的房间墙体本来就在 `innerBounds` 之外**，遍历内界天然拿不到墙。
- 标准房间模板（`RoomTemplatesGenerator`：tiny/small/normal/large/giant/colossal/soaryn）**都没有地板**：`RoomTemplate.optionalFloor` 是 optional 字段，只有 `farming` 模板显式给了 `Blocks.GRASS_BLOCK`；地板是在 `CompactMachines.newRoom` 里 `optionalFloor.ifPresent(...)` 才铺到 `innerBounds` 的**最底层**。
- 结论：**"只显示机器装置"＝"只取 `innerBounds` 内的非空气方块"**，无需额外过滤。仅剩两个边角情况需要处理：
  1. `farming`（或第三方带地板模板）：可跳过"最底层且整层同一种方块"的那一层；
  2. 玩家自建的地板/装饰会一起被显示——**这是玩家自己的作品，应当保留**。
- 房间内部尺寸 = `RoomTemplate.internalDimensions`（normal = 7³，上限 45³），正好是我们要的预览网格尺寸。

### 2.1c 几何：展示容积约 14³

`factory_casing` 实测为 1px 厚壳 + 2×2 角柱，且方块已是 `noOcclusion()`（`ModBlocks` FACTORY :41-47）→ 内部可用空腔约 **14×14×14 px**。7³ 房间映射进去 ≈ 2px/格，视觉可辨；13³ ≈ 1.08px/格，接近极限。

### 2.3 现有工厂渲染与应力语义

- `client/FactoryVisual`（Flywheel 视觉）：六方向各一个 `RotatingInstance`，模型 `AllPartialModels.SHAFT_HALF`，构造时一次 `rotateToFace` 固定朝向，运行时只切可见性。
- `client/FactoryRenderer`（vanilla BER 兜底）：`renderSafe` 先 `super(...)`（基类内部已按 Flywheel 可用性早退），再 `if (supportsVisualization) return;`。
  → **要加"预览渲染"，必须放在这个早退之前**。配套事实：`ClientSetup`（:79）注册 visual 时是 `.skipVanillaRender(be -> false)`，所以**即使 Flywheel 开着，vanilla BER 仍每帧被调用**——预览走 BER 是可行的；但 BE 没有客户端 ticker（`FactoryBlock.getTicker` :218-228 客户端返回 null），若将来要做动画得客户端自驱动。
  → **疑似既有缺陷（需实验验证）**：`super.renderSafe` 会用 `getRotatedModel`（返回整块方块模型）走 `renderRotatingBuffer` → 整块模型被施加旋转；同时 `RenderShape.MODEL` 已经把方块模型静态画过一遍 → 无 Flywheel 时疑似"整块模型画两遍、其中一遍被旋转"。立方体外壳不易察觉，但加展示罩/底座后可能暴露。动手时一并实测。
- `AllPartialModels.SHAFT_HALF` 实测模型：`[6,6,8] → [10,10,16]`，即 **8px 深、4×4 截面**——这就是"太长"的那根；短的桩只需自建一个 3~4px 深的 partial model。
- `FactoryBlock`：`KineticBlock`（无 FACING，避开旋转菜单），六个布尔属性 `shaft_north/…/shaft_down`；`hasShaftTowards(...) = state.getValue(SHAFT_BY_FACE.get(face))`；`getRotationAxis(...)` = 第一个开启面的轴；扳手点击面 toggle，并**共轴约束**（开新轴向自动关其它轴向）。
- 客户端同步范式已有：`StressProfile` 走 NeoForge **attachment + `STREAM_CODEC`**；0.3.49 的观察者功能已有自定义网络包范式（`ModNetworking`）。

## 3. 技术方案草案（四块）

### 3.1 快照采集与存储（服务端）

**采集时机**：固化（SOLIDIFYING）时从 **eval_world 副本**取（那一刻副本必然已加载、内容 = 评估结束态），避免依赖源房间是否加载。

**编码**：调色板 + 稀疏索引
```
{ w,h,d, palette:[ "create:shaft[axis=y]" , ... ], cells:[ (packedXYZ, paletteIdx), ... ], count }
```
- 只存**非空气**格子；palette 用原版 `BlockState` 字符串形式（`BlockStateParser` 可逆）。
- 体积估算（7³ 房间、~150 非空气块）：调色板 ≈ 1 KB 文本 + 每格 5 B ≈ **2 KB 上下**，压缩后更小。13³ 约 4~8 KB。
- **上限与降级**：配置项（如 `previewMaxCells`，默认建议 4096）。超限依次降级：① 只取"非空气包围盒"；② 按步长稀释（每 k 格取 1）；③ 放弃快照，退化为纯外壳（并给 tooltip 提示）。

**存储**：`FactoryBlockEntity.save/read` 增一个 `preview` 子标签。旧档无此键 → 无预览，行为不变（**存档兼容天然成立**）。

### 3.2 同步到客户端：**不需要新网络包**（实测结论）

- `FactoryBlockEntity.write(...)`（:1537）**没有按 `clientPacket` 分支**，即服务端每次 `sendData()`（:429/:520）推给客户端的 update tag 里就是**全量 NBT** → 预览数据只要写进 NBT 就会自动到客户端。
- 也就是说：**把 `preview` 子标签写进 `write/read`，客户端 `getUpdateTag`/`read(clientPacket=true)` 即可拿到，零网络代码。**
- 代价与护栏：① 每次 `sendData()` 都会带上预览负载（应只在快照变化时标记同步，或让 `sendData` 的频率不被预览放大）；② BE 更新包受 21-bit 帧长（≈2 MB）限制——单工厂 2~8 KB 无压力，但**必须加体积上限**；③ 服务端 BE NBT 本身目前**没有任何护栏**（REPLAY 极端情况下 pattern 表可达数百 KB），加预览前建议先加一个"预览不得超过 N KB，超限降级"的硬阈值。

### 3.3 客户端渲染

1. 收到快照 → 构建 `Map<BlockPos, BlockState>`（复用 `SchematicLevel` 或自建 `VirtualRenderWorld` 子类，`supportsVisualization()→false`）。
2. **烘焙一次**：照 `SchematicRenderer.drawLayer` 的思路，逐 `RenderType` 用 `ShadedBlockSbbBuilder`/`ModelBlockRenderer.tesselateBlock` 把整份结构烘成若干 `SuperByteBuffer` 并缓存；数据变/资源重载时失效重烘。
   - **比 PE 逐格渲染更省**（PE 每帧 343 次姿态变换 + 模型渲染；我们是 1~3 次 draw）。
   - 烘焙放到"有预算的懒执行"（每帧最多烘一个工厂），避免首帧尖峰。
3. 渲染：在 `FactoryRenderer.renderSafe` 里 push/translate(缩放中心/底座偏移)/scale(≈1/N)，按 RenderType 把缓存 buffer 画出来；光照用 `setExternalLight` 或固定值。
4. **LOD**（必须）：距离超过阈值只画不烘（或干脆不画）；远离视锥不处理。可选：极远处用"占位色块"。
5. **不做的部分（MVP）**：内部 BE（箱子/告示牌/皮带物品）、运动件动画。这些是 PE 花最多代码的地方（`PrecisionBeltRenderer` + `renderBareKinetic` + 代理 BE 每 tick），可以二期再加（见 §6 Q4）。

### 3.4 模型改造（底座 + 展示罩）

- 现状：`factory_casing`（1px 厚外壳框架）+ `factory_panel`（4..12 的 8×8 面板）+ `factory_fill`，六面 multipart 按开口切换。
- 新形态：**下半部/底部为实心安山机壳底座，上方为可透视的展示罩**；展示体积建议留出内缩边界（例如 2px 边框），使微缩内容不被外壳压住（PE 是把 7³ 铺满 16³、外壳压住最外圈，属于"将就"做法）。
- 纯资源工作：新 `factory_base.json` / `factory_cage.json`（玻璃/镂空） + 贴图；`factory_block.json` multipart 相应改写。

### 3.5 应力接口 + 短轴渲染

- **短轴**：新建 `ModPartials.FACTORY_SHAFT_STUB`（例：`[6,6,13]→[10,10,16]`，3px 深）→ `FactoryVisual` 用 `Models.partial(ModPartials.FACTORY_SHAFT_STUB)`，`FactoryRenderer` 用 `CachedBuffers.partialFacing(ModPartials.FACTORY_SHAFT_STUB, state, d)`。**两个注册点都要改**（Flywheel + 兜底），否则会出现"有 Flywheel 时长了/无 Flywheel 时短了"的不一致。
- **模型 JSON 路径**：按 skill `references/16`，自定义部件模型放 `assets/createcmpor/partial/block/<name>.json`（**需实验验证**：catnip `PartialModel.of` 的实际查找路径，Create 的 `AllPartialModels` 走的是 `block/` 下带特殊前缀的烘焙注册，附属项目建议实测一次）。
- **只有底座接应力**：改 `hasShaftTowards`/`getRotationAxis`/扳手逻辑。影响面实测：
  - **最小集（5 处）**：`FactoryBlock.hasShaftTowards`(:232)、`getRotationAxis`(:237)、`onWrenched`/`toggleFace`(:88-115)、`FactoryBlockEntity.firstOpenFace`(:1774)。缺点：会出现"能拧开但不起作用的面"，交互不一致。
  - **彻底集（约 13 处）**：另需同步 `assets/createcmpor/blockstates/factory_block.json` 的 12 个条件 part、`ModBlocks.isFactoryIoFace`(:166)、`IOExtensionBlockEntity`(:103/:156/:174)、`IOExtensionScenes`(:67)、`areStatesKineticallyEquivalent`(:192)，以及 Ponder/文档。
  - **必须保留六个 `shaft_*` 属性**（旧存档 palette 兼容，见 §6 Q3 硬约束）。
  - 注意 Create 语义：**轴永远从"面中心"（y=8 那一圈，4×4 截面）接入**，所以"底座只占底部 4px"与"侧面能接轴"在几何上互斥（侧面轴会插进展示罩）。这是 §6 Q3 必须拍板的原因。

## 4. 风险与坑（按优先级）

| # | 风险 | 说明与规避 |
|:--|:--|:--|
| 0 | **`supportsVisualization()→false` 必须写** | 漏写 = 微缩内容整块不渲染且**无任何报错**（Flywheel 抢答 + Create 渲染器早退）。这是第一号坑 |
| 1 | **BER 早退顺序** | `FactoryRenderer.renderSafe` 现在先 `super()` 再判 Flywheel 早退；预览渲染必须放在两者之前，否则"有 Flywheel 的玩家看不到预览、无 Flywheel 的玩家看得到"这种诡异 bug |
| 2 | **烘焙成本与抖动** | 一份 343 格结构烘一次约几十万顶点操作；必须懒烘 + 每帧预算 + 缓存失效策略，否则多工厂同屏会卡顿 |
| 3 | **存档与网络体积** | 每个工厂存一份房间快照；实测 BE NBT 目前**无任何体积护栏**（REPLAY 极端可达数百 KB），必须同时加"预览硬上限 + 超限降级"。多工厂组（`factory_count>1`）会 N 倍叠加 |
| 3b | **固化窗口唯一** | 快照只能在固化流程里采（之后源房间已卸载、staging 已删、manifest 只有区块 hash）。采集失败要有明确兜底（无预览，不影响固化正确性） |
| 3c | **副本 ≠ 冻结源态** | eval 副本是克隆体，理论上与源房间一致，但若房间在克隆期被改动/克隆失败路径，预览会与玩家记忆不符。需要确认"取哪一份"并在 tooltip/文档说明 |
| 4 | **大房间（soaryn 45³）** | 45³=91125 格缩进 12px → 单格 0.13px，纯噪点。必须按"非空气包围盒取景 + 上限降级"而不是按房间尺寸缩放 |
| 5 | **内部 BE / 运动件** | MVP 不做则箱子/皮带不会显示细节（皮带可能整段不渲染 —— PE 为皮带专门写了 renderer）。需明确告知玩家/或二期补 |
| 6 | **模型与微缩内容互相穿插** | 展示罩内净空不够时微缩方块会"穿模"到外壳里。设计阶段先定净空（建议 ≥14³ 或外壳 2px） |
| 7 | **旧档** | 无快照字段 → 无预览（可接受）；但**模型改造是全量的**，老工厂会一起变外观，需用户确认可接受 |
| 8 | **纹理与缩放** | 1/7~1/12 缩放下的贴图闪烁/摩尔纹（PE 同样存在）。可用 `RenderType` 选择、mipmap、或"远处只画剪影色块"缓解 |
| 9 | **蓝图/掉落物** | 工厂掉落携带完整 BE NBT（已有），快照会被一起复制 → 体积翻倍；需在 `CreateNbtSanitizer` 路径确认是否要剥离 |
| 10 | **性能上限** | 同屏 N 个工厂 × 每个 1~3 个 buffer；建议加客户端距离门槛 + 配置总开关 |

**未验证项（需实验）**：自定义 partial model 的确切资源路径；`VirtualRenderWorld` 在 BER 内被反复 push/scale 渲染的实际帧耗；attachment 同步在大量工厂时的实际带宽。

## 6. 已拍板决策与新增课题（2026-09-29 用户确认）

| 决策点 | 结论 |
|:--|:--|
| 对象方块 | **平行工厂方块（固化产物）**，快照在固化时采 |
| 展示内容 | **只显示机器装置**——即 `innerBounds` 内的非空气方块（天然排除墙体，标准模板无地板，见 §2.1b） |
| 底座/应力 | **方案 A**：底座在方块底部，**只有底面接应力**（轴恒竖直），传动杆只在底座渲染一小节 |
| 动画 | **首版纯静态**（可后续再加内部运动件） |
| 六面开口玩法 | **保留**：默认 = 展示模式；玩家用**安山机壳"包壳"**后回到现有六面开口模式 |

### 6.1 包壳机制（Create 源码实测，`content/decoration/encasing/`）

**Create 提供了一整套公共 API，可直接复用：**

| 类 | 作用 |
|:--|:--|
| `EncasableBlock`（接口，public） | 标在"裸方块"上；`tryEncase(state, level, pos, heldItem, player, hand, ray)` 需在 `useItemOn` 里调用——它会遍历 `EncasingRegistry.getVariants(state.getBlock())`，用 `EncasedBlock.getCasing()` 与手持物品比对，命中则调 `handleEncasing(...)` 并播放包壳音效 |
| `EncasedBlock`（接口，public） | 标在"包壳后的方块"上；`getCasing()` 返回机壳方块、`handleEncasing(...)` 负责换方块 |
| `EncasingRegistry`（public） | `addVariant(encasable, encased)` 建立映射（**必须在方块注册完成后调用**）；也有 Registrate 版 `addVariantTo(...)` |

**机制细节（逐条实测）：**

1. **包壳不消耗机壳物品**——`EncasableBlock.tryEncase` 全流程**没有任何 `shrink(1)`**；`EncasedShaftBlock.handleEncasing` 也只是 `switchToBlockState`。用户"不消耗安山机壳"的判断**正确**。
2. **去壳 = 潜行 + 扳手**，不是"破坏后重新放置"——`EncasedShaftBlock.onSneakWrenched` 会 `switchToBlockState(level, pos, 裸方块同轴状态)` 并播放破坏粒子。**用户这里的描述需要纠正。**
3. **破坏掉落只掉裸方块**：`data/create/loot_table/blocks/andesite_encased_shaft.json` 只出 `create:shaft`（机壳不掉）。
4. **BE 数据保留**：走 `KineticBlockEntity.switchToBlockState(level, pos, newState)`（:381）——必要时先 `detachKinetics()/removeSource()`，再 `setBlock(pos, state, UPDATE_ALL)`；原版 `LevelChunk.setBlockState` 会**复用同一位置上的 BE 实例**（只要新方块仍是 `EntityBlock`）。
5. 另配套 `SpecialBlockItemRequirement` + `getCloneItemStack`（创造模式中键取哪个物品，取决于是轴面还是机壳面）。

### 6.2 我们的接入方案（推荐，已按实测证据修正）

> ⚠️ **不要用 `EncasingRegistry`，也不要做"两个方块"。** 下面的证据链决定了这一点。

**致命约束：跨方块包壳会丢光 BE 数据。**

- Create 的 shaft ↔ encased_shaft 是**两个不同方块 + 两个不同 `BlockEntityType`**，两者的 `validBlocks` 互不包含 → 原版 `LevelChunk`（sources :288-299）会**销毁旧 BE、新建一个**，再由 `IBE#onRemove` 补一刀。
- 所以 Create 那边"包壳后转速无缝"**并不是数据延续**，而是新 BE 的构造器带 `updateSpeed=true` 重新挂上动力学网络。
- 我们的 `FactoryBlockEntity`（1837 行）里装着 roomCode、`restore_state`/`restore_machine`、pattern/rate 表、`FactoryIndexSavedData` 索引、评估状态——**跨方块包壳等于全部清零**。这条直接判死刑。（若有人坚持双方块，唯一补救是把两个方块登记进**同一个** `BlockEntityType`：`Builder.of(supplier, blockA, blockB)`。）

**✅ 推荐：单方块 + 新增 `encased` 布尔属性 + 自写交互**

- 保留方块 id `createcmpor:factory_block` 与全部六个 `shaft_*` 属性（旧档 palette 兼容）；
- 新增 `BooleanProperty encased`，**属性默认值设为 `true`**（旧存档 palette 缺该属性 → 取默认值 → 老工厂继续是传统模式，玩家现有应力布局不受影响；`StateDefinition` sources :75-83 + `StateHolder` :168-179 提供原版编解码器背书）；
- `getStateForPlacement` 显式返回 `encased=false`（**新放置 = 默认展示模式**）；
- 展示模式：只在底面（DOWN）接应力、轴恒 Y、模型 = 安山机壳底座 + 展示罩、BER 渲染微缩预览；
- 包壳：手持 `create:andesite_casing` 右键 → `encased=true`（**自己写 `useItemOn`，约 10 行**：判断手持物 == 机壳 → `switchToBlockState` + 播放包壳音效；音效公式照抄 `EncasableBlock#playEncaseSound`：新方块 place 音、`(vol+1)/2`、`pitch*0.8`）；
- 单方块的关键收益：**BE 实例与 NBT 100% 保留**（原版 `LevelChunk` :299 走 `blockentity.setBlockState(state)`），单物品、单 loot table、单 BE 类型，资源与回归面最小；
- **同构先例就是 Create 自己的皮带**：`BeltBlockEntity$CasingType{NONE,ANDESITE,BRASS}` 存在 BE 里、方块只加一个布尔 `BeltBlock.CASING`，`BeltBlock#useItemOn` 手写两种机壳、**完全不用 `EncasingRegistry`**。判据：包壳是否改变几何/拓扑——我们和皮带一样，不改变方块身份。

**必须同步改的地方（否则动力学不重建）**

- `FactoryBlock.areStatesKineticallyEquivalent`（:192）要把 `encased` 纳入比较：**只要新属性会改变 `getRotationAxis`，就必须返回 `false`**；返回 `true` 会导致"永不重挂"（`KineticBlock#updateIndirectNeighbourShapes` 的重挂钩子需要 `(flags & 16) == 0`，而 `switchToBlockState` 用的 `UPDATE_ALL = 3` 恰好满足）。

**手势冲突已决（2026-09-29 用户拍板）：两段式**

现有 `FactoryBlock.onSneakWrenched` = "潜行扳手取下工厂（掉落携带完整 BE NBT）"，与 Create 惯例"潜行扳手 = 去壳"撞车。用户选定：**有壳（`encased=true`）时潜行扳手 = 去壳；无壳时才拆下掉落**。与 Create 肌肉记忆一致，且普通挖掘本来就会掉落带 NBT 的工厂物品，功能不丢。

## 7. 手持/物品栏的微缩预览（子课题结论）

**参考模组 PE 没做这件事。** 全工程 grep `IClientItemExtensions|getCustomRenderer|BlockEntityWithoutLevelRenderer|renderByItem` **零命中**；它的物品模型是普通模型（非 `builtin/entity`），`EngineeringPreviewRenderer` 是"世界坐标里的幽灵预览"（唯一调用点 `PrecisionSpaceRenderer.java:118`，签名里没有 `ItemStack`）。**PE 手里拿着微缩方块时只看到静态外壳**——它实际就停在用户说的"退回当前模型"。

**我们这边：可行，中等工作量（约 400~600 行 + 1 个 item model JSON），且比方块侧更省事**（不需要 BER、不需要 Flywheel visual、不需要网络协议——快照本来就随 `BLOCK_ENTITY_DATA` 组件同步，`dropFactoryWithData` 已带全量 BE NBT）。

**最小路线**：

1. 物品模型 JSON 改为 `"parent": "builtin/entity"` —— **这是触发器**：不改则 `renderByItem` 永不被调用且无任何报错（`ModelBakery` :76-78 → `BuiltInModel` :51-53，`ItemRenderer` :125/:156 靠 `BakedModel#isCustomRenderer()` 分流）；副作用是原版 quad 路径被跳过，**外壳得自己画**。
2. `RegisterClientExtensionsEvent#registerItem` 注册 `IClientItemExtensions#getCustomRenderer()`（`Item#initializeClient` 已弃用）。
3. `BlockEntityWithoutLevelRenderer#renderByItem(ItemStack, ItemDisplayContext, PoseStack, MultiBufferSource, int, int)`（**6 参、没有 Level**）；进入时坐标已是方块自身 0..1 空间（`ItemRenderer` :123-124 已 `translate(-0.5,-0.5,-0.5)`）。
4. 读快照：`stack.get(DataComponents.BLOCK_ENTITY_DATA)` → `CustomData.getUnsafe()` → 调色板用 `NbtUtils.readBlockState(BuiltInRegistries.BLOCK.asLookup(), tag)`（只吃 `HolderGetter<Block>`，**不需要 level**）。
5. 与方块侧**共用同一份预览实现**（`NonVisualVirtualRenderWorld` + 按快照哈希的 LRU 缓存 + 1/N 缩放逐格 `renderBatched`），最后 `finally resetExternalLight()`。

**手持预览专属的坑（按危险度）**：

| # | 坑 | 后果 |
|:--|:--|:--|
| 1 | `level == null` 时构造 `VirtualRenderWorld` | 构造器首行就解引用 `level.getLevelData()` → **NPE**；必须降级为"只画外壳" |
| 2 | `renderByItem` 里抛异常 | 走 `GuiGraphics` 路径直接 **崩溃游戏**（ReportedException）→ 必须 try/catch 降级 |
| 3 | 对 `ENTITYBLOCK_ANIMATED` 状态调 `renderSingleBlock` | 会回调 `renderByItem` → **无限递归** |
| 4 | 漏写 `supportsVisualization()→false` | 整块不渲染、零报错 |
| 5 | 每帧 × 物品栏数十槽位 × 343 格 | 必须缓存 + LOD（1.21.1 无 `ItemStackRenderState`，**每帧每次绘制都会调**） |
| 6 | 缓存 BakedModel 跨资源重载 | 自定义 BELWR **不会**被自动注册为 reload listener，需自己清缓存 |
| 7 | 快照进物品组件 | 需体积上限（建议 ≤2~4 KB，超限降级为"只画外壳"） |

**结论**：**可以做，但已拍板排在方块侧预览跑通之后**（共用实现，边际成本才低）。在方块侧完成前，手持沿用当前静态外壳模型（**这正是 PE 的现状**，可作为可接受的对照）。

1. **对象方块**：「评估工厂」= 平行工厂方块（固化产物）？还是评估方块（评估中）？还是两个都要？
2. **展示内容**：房间内全部非空气方块（连地板/墙）／只显示机器装置／只显示非空气包围盒内内容？
3. **底座与应力接口形态**（几何互斥，必须选）：
   - A 同一方块内：底部实心底座 + 上方展示罩，**仅底面**接应力（轴恒为竖直）
   - B 同一方块内：底座占下半，底座**四侧 + 底面**接应力（轴可为 X/Y/Z）
   - C **独立底座方块**，工厂叠其上，应力只从底座进
   - D 保留现有**六面开口**语义，只把传动杆渲染改短
   > 硬约束（Create 语义）：传动轴永远从**面中心**（y=6..10 那 4×4 截面）接入。所以"底座只占底部 4px"与"侧面接轴"在几何上互斥——侧面轴必然插进展示罩区域。选 A/B/C 时都要先画一次剖面对齐。
   > 硬约束（存档）：**六个 `shaft_*` 属性不能删除**——旧存档 blockstate palette 里带这些属性，删属性会导致状态解析失败（方块丢失/变空气）。改语义只能"保留属性、改判据"。
4. **静态 or 动态**：纯静态（推荐首发）／内部轴齿轮跟随转速／连皮带物品都动
5. **是否保留"六面开口"作为可切换模式**（扳手切换"展示模式/接口模式"），还是直接替换？
6. **大房间降级策略**与**默认开关**（是否默认开启预览）。
