## 2. 【高危缺陷】可触发性校验对 REPLAY 分支必然误判

**严重度：高（阻塞验收项 B4；且阻塞一切"含并行方块且存在 REPLAY 分支"的房间固化）**
**性质：跨模块接口不匹配（评估侧 → 校验侧），编译期不可见**

### 2.1 证据链（三处代码，缺一不可）

**① REPLAY 判定分支把 `inputRates` 留空**（`EvaluationVerdict.decide`，REPLAY 构造点）：
```java
return new Result(VERDICT_REPLAY, null, Map.of(), Map.of(),
        replay.replayIn(), replay.replayOut(), …);
```
`Result` 的字段顺序为 `(verdict, rejectReason, inputRates, outputRates, replayIn, replayOut, …)`
（`public record Result(...)` 头部已核对）⇒ **`inputRates` = 空 Map**，REPLAY 分支的真实输入在 `replayIn`。

**② 校验只读 `inputRates`**（`EvaluationVerdict.untriggerableModes`）：
```java
for (EvaluationTrace.FlowKey key : mode.inputRates().keySet()) {   // ← REPLAY 时恒为空集
    if ("item".equals(key.kind())) {
        inputSignatures.add(key.signature());
    }
}
```
（同处 javadoc 也自述"该分支输入表签名集 = `inputRates` 的物品 flow key"。）

**③ 固化侧对**全部**结果调用该校验**（`EvaluationCloneManager`）：
```java
List<Component> untriggerable = EvaluationVerdict.untriggerableModes(results);
if (!untriggerable.isEmpty()) { … notifyOwner(…); requestCleanup(…); return; }
```

### 2.2 后果推导

- REPLAY 分支 + 触发物品非空 ⇒ `inputSignatures` 为空 ⇒ `anyTriggerable = false` ⇒ 计入 `problems`。
- ⇒ `untriggerable` 非空 ⇒ **整场固化取消**（`requestCleanup` + "存在无法触发的模式"提示）。
- 触发物品来自并行空间输入方块 ⇒ **凡是"并行方块 + 任一分支被判 REPLAY"的房间，固化必然失败**。
- 0.4.31 无此校验 ⇒ 这是**本重构新引入的回归**；验收项 **B4（RATE/REPLAY 混合分支固化）必挂**。
- 实机表现：评估跑完、副本清理、**什么都没生成**，玩家收到"某模式不可触发"的误导提示（真正原因是框架把 REPLAY 的输入表当空表）。

### 2.3 修复方向（不指定实现，交由 Lead 决策）

任选其一即可消除误判：
1. 校验侧的签名集**同时**并入 `replayIn()` 的物品 flow key（与 RATE 的 `inputRates` 取并集）；
2. 或在 REPLAY 构造点**用 `replayIn` 派生一张等价的 `inputRates`** 一并填入（保持"输入表"单一来源）。

> ⚠️ 提醒：修完后 `E2.4` 会自动转 PASS，请让脚本重跑确认，不要只改代码不复验。

## 4. 对抗性复核（本轮重点项，逐条给结论）

### 4.1 候选排序改为「命中触发物品数最多者优先，并列取索引最小」—— ✅ 【代码确证 + 推演】

- `refreshActiveMode()`：遍历模式，**跳过默认模式**，`triggerHits(mode)` 取命中数，
  `if (hits > bestHits)`（**严格大于** ⇒ 并列自然保留索引最小者），无候选回落 `defaultModeIndex()`。
- `triggerHits()`：`for (String signature : mode.triggers)`，`container != null && container.amount >= 1` 则 `hits++`。
- **静默死模式反例**（Lead 提出的 {沙,木棍} vs {沙}）：喂「沙+木棍」时
  {沙,木棍} 记 **2** 分 > {沙} 记 **1** 分 ⇒ 高特异模式可达。**反例不成立，问题已解决。**
- **确定性（I4）保持**：计数是输入的纯函数，并列由索引裁决 ⇒ 同输入必得同一模式。

> 但请注意一个**残留可达性缺口**（低危，供裁决）：见本节 4.4。

### 4.2 秒槽指针「只在兑现成功后推进一次」—— ✅ 【代码确证】

不只看 `setActiveMode` 的保存/恢复两行，独立核对推进点（`tickReplay`）：
```java
if (replayIsReady(replayCurrentSecond)) {
    replayApply(replayCurrentSecond);
    replayCurrentSecond = (replayCurrentSecond + 1) % patternLength;   // 唯一推进点
    lastSuccess = true;
} else {
    lastSuccess = false;                                               // 未兑现 ⇒ 指针不动
}
```
且 `replayIsReady(second)` **同时**检查输入是否够、输出是否有空间（两者都以 `second` 索引取值）。
⇒ 指针单调 `+1 mod L`，长期速率 = `ΣP / L` = 单机产能，**不可白嫖推进、不可峰值秒复用**。
与已修订的 47 §7.3「绝不回卷」一致（脚本 `X3.2` = doc↔code 一致性检查，现 PASS）。

### 4.3 燃料槽不随激活模式变化 —— ✅ 【代码确证】

- `fuelSlotIndex()` = `fuelSlotPresent ? inputSlotTotal() + outputSlotTotal() : -1`——**不读** `activeMode`。
- `getSlots()` = `inputSlotTotal() + outputSlotTotal() + (fuelSlotPresent ? 1 : 0)`——同样不读激活模式。
- `acceptFuelAnyMode(stack)`：用 `anyModeNormalBurn` / `anyModeSuperBurn`（**任一模式需要即成立**），
  **未**使用 `burnModeActive()`（后者才是"当前模式"口径）⇒ 接受判据稳定。
- 与"要不要烧"解耦：`tickBurner()` / `burnerSatisfied()` 走 `burnModeActive()`（当前模式），
  所以"收下燃料"不会导致非燃烧模式白烧。
⇒ 外部设备跨 tick 缓存的槽位索引不会在切换瞬间漂移（原注释担心的"物品凭空销毁"路径被堵死）。

### 4.4 残留缺口（低危，供产品裁决）：放宽后的校验 + 新排序 ⇒ 仍可能出现"实践上不可达"的模式

- `untriggerableModes` 已**放宽**为"**至少一个**触发物品可喂即可"（javadoc 说明：多并行方块时
  触发集是各方块第 i 项的**并集**，若坚持"全部可喂"会误伤 0.4.31 能固化的合法房间）。
- 构造：模式 0 触发集 `{沙}`，模式 1 触发集 `{沙, 木棍}`，而**木棍不在模式 1 的输入表**（无槽可喂）。
  - 校验：`沙` 可喂 ⇒ 通过 ✅
  - 运行：喂「沙」→ 两模式各命中 1 ⇒ 并列取小 ⇒ **模式 0**；喂「沙+木棍」→ 1 vs 2 ⇒ 模式 1，
    但**木棍喂不进去** ⇒ 模式 1 实践上不可达。
- **影响**：该模式永远不激活（浪费 NBT + 困惑），**但不是安全漏洞**（互斥仍成立，不超产）。

#### ✅ 裁决（Lead 2026-10-05）：**不处理，记为已知行为**

| # | 理由 |
|:--|:--|
| ① | **不影响安全**：互斥（I2）仍在，任一 tick 至多一个模式兑换，不产生超产面；本缺口只造成"某模式点不亮" |
| ② | **"剔除不可喂的触发物"这条看似合理的修法有陷阱**：若某模式的触发集被**剔空**，该模式就变成 `triggers.isEmpty()` ⇒ 被 `Mode.isDefault()` 判为**默认模式**，从而**无条件激活**——把"点不亮的模式"变成"始终激活的模式"，方向反而更危险 |
| ③ | **收紧判据会误伤合法房间**：多并行方块配置下触发集是各方块第 i 项的**并集**，要求"每一项都可喂"会把 0.4.31 能正常固化的房间整场取消（这正是该校验此前已被放宽一次的原因） |

⇒ 已知行为记录在案；实机观察步骤见 [manual_test_steps.md](manual_test_steps.md) **B7**
（该步骤明确要求：**记录现象即可，不要判为漏洞**）。

> 💡 若未来要真正消除该缺口，正确方向不是"校验更严"，而是**运行期**让不可达模式不占用 NBT/展示
