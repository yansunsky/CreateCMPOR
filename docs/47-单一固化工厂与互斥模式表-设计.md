# 47 · 单一固化工厂 + 互斥模式表（设计草案 v1）

> 版本线：0.4.31 之上（0.5.0）
> 状态：**待用户确认**；确认后进入实现。
> 决策来源：2026-10-05 两轮需求澄清（用户口述漏洞 + 8 项选择题）。

---

## 1. 背景：被报告的漏洞

### 1.1 现象（用户实机口述）

> 「某空间内设计了一套精密的机器，通过刷石机生成铁块，内置刷石机，所以原则上这是一个纯输出的机器，其消耗了很多原料打造。现在只需要一个并行方块，通过限流的方式让它缓慢输出某种廉价的，例如沙子，木棍，到销毁装置中销毁，就会被误认为是原料，配置了多种不同廉价原料的机器被成功的评估出了多个子机器。这样轻松实现了产线的扩张。」

复现链：

1. 房间里一台**纯输出**产线（如内置刷石机 → 铁块，建造成本高，运行不需要外部原料）。
2. 放**一个**并行空间输入方块，白名单配 N 种廉价料（沙子、木棍…），每种各配一条"限流 → 销毁装置"的支路。
3. 触发评估：每条分支评估时，并行方块只暴露第 i 个物品；廉价料经 IO 输入 → 被销毁装置销毁。
4. 三扫描把"被销毁的廉价料"如实记为**该分支的输入**，把铁块记为**该分支的产出**。
5. N 个分支 → 固化出 **N 个工厂方块**，每个都是完整产能，输入要求=廉价垃圾、产出=铁块。

一次建造成本 → N 份产能。这就是"产线扩张"。

### 1.2 代码事实（只读调研确证）

| 事实 | 位置 |
|:--|:--|
| 分支数 = 房间里所有并行方块白名单条目数的**最大值**（与方块数量无关，一个方块配 N 条就是 N 分支） | `EvaluationManager.parallelBranchCount` `EM:145-173` |
| 分支数**无硬上限**（>8 条仅退回串行，照样跑完） | `EvaluationCloneManager:389-393`、`ParallelEvaluationWorlds.LANE_COUNT=8` |
| 每个分支 = 一次完整评估（并行 lane 共用同一份源 staging；串行则每分支重新克隆） | `ECM:449-466`、`ECM:1081-1091` |
| 固化：**N 个结果 → N 个工厂方块**，主位置 + 垂直向上堆叠 | `ECM:670-781`（`count=results.size()` `:687`；堆叠 `:704`） |
| N 个工厂运行时**完全独立**：各自 tick / 各自 I/O 缓存 / 各自应力档案，代码中**不存在任何组级共享或产能上限** | `FBE:582-641`、`FBE:161-199`、`FactoryStressAccess.set`（唯一写点 `FBE:435`） |
| 组合并只发生在"元数据/索引/组还原"层面 | `FBE:248-253`、`FactoryIndexSavedData`、`FB:544-592` |

### 1.3 根因分解（**关键**）

漏洞有两层，必须分开看：

1. **外层**：一个分支 = 一个独立工厂方块 → **N 份独立产能**。
2. **内层**：**同一台机器被评估了 N 次，每次的产出都被当成一份完整产能记录下来**。

> ⚠️ 因此"只产出一个固化工厂"只解决外层。若新工厂的多个模式**能同时激活**，内层漏洞原样回归（喂沙子+木棍 → 双份铁块）。
> **互斥是本次重构的第一铁律，不是可选优化。**

历史上 [工作日志.md:2433-2460](工作日志.md) 的旧设计恰恰写着"多分支可同时激活，消耗求和"——那条设计**不可原样复活**。当年放弃它的理由只是"消灭复杂度"，与安全无关。

## 2. 目标与非目标

### 2.1 目标

- **G1**：一次评估**只固化一个工厂方块**，无论评估了几个分支。
- **G2**：工厂内部保存 N 个**互斥模式**，运行时按输入决定当前模式。
- **G3**：工厂总吞吐 ≤ 单次评估测到的单机产能（**产能守恒**）。
- **G4**：保留并行/串行评估管线（多分支采样照旧）。

### 2.2 非目标（明确不堵）

| 现象 | 处置 | 理由 |
|:--|:--|:--|
| 纯输出产线（刷石机等）固化出的工厂**凭空产出** | **不堵** | 工厂玩法的核心：一次性建造成本换产能 |
| **多个模式产出相同**（同一产线被采样 N 次） | 不堵 | 互斥后无产能叠加收益，仅多占 NBT |
| 玩家注入垃圾被记为输入 | 不堵（且**会自损**，见 §7.4） | 三扫描如实记账，无法区分"真原料"与"注水" |
| RATE 输入超额兑换（1 单位换满一 tick） | **另开一轮**（见 §11 待办） | 与并行无关的独立超产面，避免混改难定位 |

## 3. 核心不变量（铁律）

| # | 不变量 | 违反后果 |
|:--|:--|:--|
| **I1** | 一次评估 → 一个工厂方块 | N 倍产能 |
| **I2** | **严格互斥**：任一游戏 tick 至多一个模式处于激活态；总吞吐 ≤ 单机评估产能 | 漏洞换皮回归 |
| **I3** | 无匹配模式 → 工厂空闲（不消耗、不产出、不推进任何进度）。**不做任何兜底模式** | 玩家无法预测行为 |
| **I4** | 模式判定必须**确定性**（同一输入状态必得同一模式） | 投料顺序可被利用 |
| **I5** | 应力档案**保守合并**为**单一档案**（消耗取最大、供给取最小），不随模式切换 | 免费应力 / 应力残留在 Create 网络 |

## 4. 数据模型

### 4.1 工厂 NBT（新模式表）

单个工厂持有 N 个模式，**每个模式自带完整的一套表**（互斥 = 不需要跨模式合并）：

```
mode_count        : int        // ≥1；N=1 时语法与旧版等价
mode_<i>_trigger  : string     // 判别物品的身份签名（ItemIdentity，可为空 = 默认模式）
mode_<i>_verdict  : byte       // 0=RATE, 1=REPLAY
mode_<i>_progress : int        // REPLAY 秒槽指针（切模式时重置为 0）

# 每模式一套（沿用现有键名，加 mode_<i>_ 前缀）
mode_<i>_input_items / output_items / burner_fuel_items
mode_<i>_input_fluids / output_fluids
mode_<i>_input_energy_capacity / output_energy_capacity
mode_<i>_input_item_rates / output_item_rates / input_fluid_rates / output_fluid_rates
mode_<i>_input_energy_rate / output_energy_rate
mode_<i>_normal_burn_demand / super_burn_demand
mode_<i>_input_item_patterns / output_item_patterns / input_fluid_patterns / output_fluid_patterns
mode_<i>_input_energy_pattern / output_energy_pattern / pattern_length
```

**共享（跨模式，全局一份）**：

- `room_code`、`installed`、`restore_state`、`restore_machine`、`preview`（预览仍只存一份，多分支内容本就相同）
- **应力档案**（attachment `createcmpor:stress_profile`）：按 I5 合并后写入一份
- **输入/输出容器容量**：取所有模式的**最大值**（各模式共用同一批槽位，容量必须能容纳最大者）
- **输入容器的物品槽位集合** = 所有模式输入表物品签名的**并集**
- **输出容器的物品槽位集合** = 所有模式输出表物品签名的**并集**

> 槽位并集是**必要**的：模式 2 的触发物品必须在工厂里有槽位，玩家才喂得进去。

**旧档读取**：顶层键（无 `mode_*` 前缀）识别为"单模式工厂"（模式 0、无触发物品）⇒ **行为与 0.4.31 逐位一致**。

**废弃键**：`branch_index`、`factory_count` 不再由新固化写入；旧档读到 `factory_count > 1` 时进入**遗留组路径**（§8）。

### 4.2 触发物品的定义

- **触发物品集合** = 该分支评估时，房间里**所有**并行方块在该 `branchIndex` 处暴露的物品签名（去重；条目数不足的方块忽略）。
  - ⚠️ **激活判定取 `ANY`（任一触发物品出现即成为候选），不是 `ALL`**：`parallelBranchCount` 取的是房间里各并行方块白名单条目数的**最大值**，所以"多并行方块"是受支持配置；此时分支 i 的触发集是各方块第 i 项的并集，只要某条支路没消耗其中一项（很常见），`ALL` 就会让该模式**永远无法激活**、甚至导致整场固化取消（2026-10-05 复核 P1-2）。
  - 安全性不依赖 `ALL`：互斥（I2）已保证不超产；而"不在输入表里的触发物品"本就没有槽位、玩家喂不进去，天然不会误触发。
- 评估期在 `activateIoBlocks` 时采集（`ESch:513-564`），随分支结果一并保存；固化时若缺失则回读源房间兜底。
- **无并行方块 → 单分支 → 触发物品为空 → 该模式是"默认模式"，始终可激活。**
- **可触发判据（2026-10-05 复核后放宽）**：对该分支取 `有效触发 = triggerItems ∩ 该分支输入表的签名集`：
  - ⚠️ **`triggerItems` 本身为空 ⇒ 跳过校验**（该模式是"默认模式"，**始终可激活**，而非"永远无法激活"）。**缺这条例外会把所有"无并行方块的单机评估"判为失败，直接打死 0.4.31 的主路径**——由 `eval-side` 在实现时发现并补上，属于本判据的必要自洽条件。
  - `有效触发` **非空** ⇒ 通过（哪怕只有一个有效）；
  - `有效触发` **为空** ⇒ 该模式永远无法激活（玩家没有槽位可喂）⇒ **整场固化失败并提示**（见 §5.3）。
  - 输入表本身的构成沿用既有语义：非简化路径 = 净额 < 0 的通道；S0 全空简化路径 = trace 中 `inputTotal > 0` 的全部通道（该路径本就不做净额判定）。
- ⚠️ **这道校验不是"注垃圾"的防线**：注入的垃圾是**净输入**（被销毁装置吃掉），天然就在输入表里，校验必然通过。真正的防线是**严格互斥**（I2）。不要为了"更严"而扩大判据——那只会误伤合法房间（复核 P1-2）。

## 5. 评估侧改动

### 5.1 保留

分支循环、8 lane 并行、退回串行策略、S0/S1/S2 三扫描、trace/stress 的 `branch:<uuid>` 采样键、观察者模式——**全部保留不动**。

### 5.2 新增：采集触发物品

- `EvaluationVerdict.Result` 增加 `triggerItems`（`List<String>` 身份签名）。
- 采集点：`EvaluationScheduler.activateIoBlocks` 设置 `setBranchIndex(branchIndex)` 的同一处（`ESch:534-550`），读取该副本中所有 `PARALLEL_INPUT` 的 `items.get(branchIndex)`。
- 并行路径下每个 lane 各自采集，天然正确。

### 5.3 新增：可触发性校验（固化前）

固化前校验每条分支的 `triggerItems` 是否都在该分支的输入表中：

- 全部满足 → 继续固化。
- 任一不满足 → 整场放弃固化，提示哪个分支的哪个物品不可触发（本地化名称）。

理由：触发物品不在输入表 = 玩家喂不进去 = 该模式永远无法激活，属于无意义的固化结果。

### 5.4 修改：失败提示本地化（用户明确要求）

当前语义**保持**：任一分支失败（REJECTED/超时）→ 整场放弃。

**但提示必须说清是哪条分支**，且物品用**本地化名称**而不是 ID：

```
message.createcmpor.evaluation.branch_failed
  = 输入为「%1$s」的分支评估失败（%2$s）
  = Branch with input "%1$s" failed to evaluate (%2$s)
```

- `%1$s`：该分支触发物品的**显示名**（`Component.translatable` / `stack.getHoverName()`），多物品用本地化分隔符拼接。
- `%2$s`：失败原因（沿用现有 reason key 的本地化文案）。
- 触发物品为空的分支显示为"（无输入）"。

## 7. 运行时语义

### 7.1 模式选择（每 tick，`FBE.tick()` 开头）

```
候选 = { i | mode_i.trigger 非空 且 输入缓存中 mode_i.trigger 数量 ≥ 1 }
激活 =
  if 候选非空         → min(候选)                    // I4：索引最小，确定性
  else if 存在默认模式 → 该默认模式（无触发物品者）      // 仅当无其它候选
  else                → 空闲（I3：不消耗不产出，不推进进度）
```

- 候选判定只看**触发物品是否在输入缓存里**，不看其它输入是否齐备（齐备性由模式自身的 `inputsSatisfied` 判定）。
- **不因"当前模式输入不足"而自动切换**到别的模式：切换必须有显式的触发物品增删。避免抖动。
- 模式索引即评估时的 `branchIndex`。

### 7.2 激活后

直接复用现有的单分支逻辑（`tickRateContinuous` / `tickReplay`），只是把"读哪张表"改成"读当前模式的表"：

- RATE：每 tick `fraction += rate`、扣输入、加输出（沿用 `FBE:675-751`）。
- REPLAY：每 20 tick 兑现一个秒槽（沿用 `FBE:785-798`）。

### 7.3 模式切换

| 项 | 规则 |
|:--|:--|
| RATE fraction | 实现在**共享 Container** 上（**不在** per-mode）；每 tick 只对**当前模式**的速率做 `+=` ⇒ `Σ(rate_i × t_i) ≤ max(rate_i) × T`，切换最多带来 <1 单位的进位，**有界、不超产**（`verifier` 独立复核确认此点安全；脚本项 `X3.3` 常驻盯防 doc↔code 一致性） |
| REPLAY 秒槽指针 | **绝不回卷**：切走/空闲时**只保存**（`mode.progress = replayCurrentSecond`），切回时从保存值恢复 ⇒ 语义是"暂停/继续"。⚠️ 本条最初写成"切走归零 ⇒ 只会少产"，**那是错的**：归零 = 每次切回都重放**同一个**高产出秒槽，玩家以 1 Hz 交替喂两个触发物品即可把"均值回放"变成"峰值秒复用"，最高放大 `patternLength`(60) 倍（2026-10-05 对抗性复核 P0-1，已通知实现者修正） |
| 输入/输出缓存 | 不清理（由玩家自行管理；同一批槽位跨模式共享） |
| 应力档案 | 不切换（I5：全局合并后一份） |
| 应力上报 | 无需重报（档案不变）；但输出型工厂的运转翻转沿用现有 `FBE:596-599`、`627-640` |

### 7.4 安全性论证

- **互斥 ⇒ 产能守恒（RATE 面）**：任一 tick 只有一个模式在兑换，且 `fraction` 位于**共享容器**上 ⇒ Σ 时间占比 = 1 ⇒ 总产出 ≤ max_i(rate_i) ≤ 单机评估产能。
- **REPLAY 面的守恒，前提是"秒槽指针绝不回卷"**：指针一旦回卷，交替投料就会让每个模式反复兑现同一个高产出秒槽（见 §7.3 的实测反例）；不回卷时，交替只会把各模式的回放时间切碎 ⇒ 总产出 ≤ 诚实回放的 pattern 总量。
- **注垃圾自损**：注入垃圾只会让工厂多出一个"喂垃圾才走"的模式；互斥下不增加任何产能，反而多一个可能抢走激活权的候选 ⇒ 玩家最优策略是**不注**。
- **交替投料无收益**：两模式交替时各自运行时间减半，Σ(rate_i × 占比_i) ≤ max(rate_i)。

## 9. 风险清单（来自只读改动面调研）

| # | 风险 | 要点 |
|:--|:--|:--|
