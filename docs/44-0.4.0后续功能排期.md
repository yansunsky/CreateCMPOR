# 44 · 0.4.0 后续功能排期（三份子代理调研汇总）

> 三份调研报告原文在 `%TEMP%\cpe-src\`：`DYNAMIC-PREVIEW-REPORT.md`、`HELD-ITEM-REPORT.md`、`FRAMELESS-GLASS-REPORT.md`。

## 0. 结论：排期建议

```
P5 无边框 + 边框玻璃包壳      ← 快速见效、零依赖、纯资源+状态+交互        ≈0.5 天
P6 预览管线三层抽离（共同改造）← 后两项功能的前置，必须只做一次            ≈0.5~1 天
P7 动态预览（A1：纯旋转部件）  ← 用户第一诉求，效果最直观                  ≈1~2 天
P8 手持/物品栏真实预览        ← 复用 P6 的 baker，收益是观感一致性        ≈1.5~3 天
P9（可选）动态第二期 A2 + 补齐静态缺件                                    ≈2~3 天
```

**为什么 P5 排最前**：它与 P6/P7/P8 无依赖（只动物块模型、blockstate、一个属性、交互与音效），能立刻拿到观感收益；而且它带出一个**必须一起改的渲染常量**（见 §2 几何重叠）。

**为什么共同改造排在动态之前**：动态（P7）要"把会动的格子从烘焙里摘出去、另走每帧窄 pass"，手持（P8）要"在**没有方块实体**的上下文里烘焙"——两者都要求把现在塞在 `FactoryPreviewRenderer` 里的烘焙逻辑拆出来。合起来抽一次，避免做两遍返工。

## 1. 共同改造（P6）：预览管线三层抽离

现状：`FactoryPreviewRenderer.java` 一个类里混着 缓存键(BE) + 烘焙 + 渲染 + 常量。

目标三层（对外签名不变，`FactoryPreviewRenderer` 降为胶水）：

| 层 | 职责 | 关键点 |
|:--|:--|:--|
| `PreviewBaked`（record） | 一次烘焙的产物：per-RenderType `SuperByteBuffer` + contentHash | **去掉 `light` 字段** |
| `FactoryPreviewBaker.bake(Level, PreviewSnapshot)` | 建 `NonVisualVirtualWorld`、写方块、代理 BE、CTM 处理、逐层 tessellate | **与 BE 无关**（手持侧只有 `ItemStack`） |
| `PreviewBakeCache` | 方块侧 `WeakHashMap<BE,..>`、物品侧 LRU(32) + `IdentityHashMap<CustomData,..>` 零哈希快路径 + 失败集 | **light 不进缓存键**，改渲染期 `.light(packedLight)`；否则第一人称/掉落物每帧重烘 |
| `PreviewRender.render(ms, buffers, light, baked)` | 纯渲染 | 供方块 BER 与物品 BEWLR 共用 |

配套：资源重载/切世界 → `clearAll()`；每帧只允许 1 次新烘焙。

## 2. P5：无边框展示 + 用 Create 边框玻璃包壳

**边框玻璃真身（jar 内资源实测）**：`create:framed_glass`，`ConnectedGlassBlock extends TransparentBlock`，**无方块实体**，`cutout` 渲染层，中文名"边框玻璃"；模型 = `cube_all` + 单张 16×16 贴图 `create:block/palettes/framed_glass`（2px 外框画在贴图内、中心 alpha=0）。

- **它是 CTM**（`OMNIDIRECTIONAL`，8×8 连通表），但**孤立方块 = tile(0,0) 与原贴图逐字节相同**，且 CTM 按 **Block 键**注册、只作用于 framed_glass 自身 → **不污染我们的方块与微缩预览**。
- 外壳**只引用贴图** + 自建薄板；**切勿引用它的 `cube_all` 方块模型**（实心，会把预览挡死）。

**模型**：
- 无边框形态 = 只留 3px 底座 5 个元素（删 4 立柱 + 4 横梁 + 4 玻璃）；
- 玻璃包壳形态 = 同几何、`glass` 贴图换成边框玻璃贴图；5 片薄板必须**扩到整面**（现内缩 `[2,3,0]→[14,15,1]`，不扩则四角有 2px 断口）；
- 两模型可做父子（子模型只覆盖 `textures`）。

**状态设计（推荐）**：**保留 `ENCASED`（默认仍 true）+ 新增 `GLASS_SHELL`（默认 false）**。
硬理由：现有 6 处 `!ENCASED` 分支语义恰好等于"新式展示形态（含玻璃壳）"，**一行不用改**；旧存档/蓝图/ponder 零迁移（`NbtUtils.readBlockState` 对未定义属性键静默忽略；Ponder 的 machine4/5 实测无 `encased` 键）。改单枚举更干净，但会让 0.4.0 已切到展示模式的工厂回落成传统模式。

**交互**：右键 `create:framed_glass` 包壳（**不消耗**，Create `EncasableBlock.tryEncase` 全路径无 shrink 为证）；音效必须用 `SoundEvents.GLASS_PLACE`（现 `playEncaseSound` 取新状态 `SoundType`，会响金属声）；去壳插入现有两段式潜行扳手（玻璃壳 → 脱壳），全程 `switchToBlockState`。

**必须一起改的渲染常量**：`BOX_PX=12 + BOTTOM_PX=3` 使内容顶到 y=15，与侧面外框顶部 2px 带 `y∈[14,16]` **重叠 1px**（几何推算）→ 建议 `BOX_PX` **12→10**。

**风险**：①误用 cube_all 方块模型；②multipart 空 `when:{}` → `Selector` 抛 "No elements found in selector" 整块加载失败；③blockstate 写未定义属性 → `KeyValueCondition` 抛异常（改属性必须同步 JSON 与 `StateDefinition`）；④共面闪烁（相邻工厂外壳，可内缩 0.01px 规避）。

## 3. P7：动态预览（第一期 A1，纯旋转部件）

**架构选择：A（混合），不是照抄 PE 的逐帧全量。** 保留静态烘焙，只把"会动的格子"摘出来放进每帧窄 pass：
- 每帧对动态格取 `KINETIC_BLOCK` compartment 缓存的 `SuperByteBuffer`，`buf.light(light).rotateCentered(angleRad, axis).renderInto(ms, vc)`；
- **关键可行性证据**：`DefaultSuperByteBuffer.renderInto()` 结尾会清空自身 transform 栈 → **同一份缓存可被 M 个格子逐帧复用，零逐格拷贝**；
- 覆盖：轴 / 齿轮 / 装箱齿轮 / 装箱轴 / 粉碎轮 / 磨石 / 变速箱 / 离合换挡 / 创造马达 / 水车 / 飞轮块 / 转盘 / 动力轴。

**不推荐**：B（每帧全量 tessellate N 格）——本项目自己的烘焙就为此限流"每 tick 最多烘一个工厂，避免帧尖峰"，一次全量已是尖峰。C（预烘 K 帧）内存 ~30MB/工厂且相位跳变。D2（shader）工程量过大。

**数据**：快照升 **v3**，增稀疏 `speeds`（varint 索引 + float；M=50~300 时 0.3~2.5 KB）。
- 取 `getTheoreticalSpeed()`，**不要** `getSpeed()`（后者 overStressed/冻结时返 0）；
- **采集时机有风险（未确认）**：现采集点在 `deactivateIoBlocks` 之后约 2 个相位，停 IO 是否归零转速未确认 → 建议把 speed 采集**前移**或取采样窗口最大 |speed|；
- 建议整表统一缩放（targetMax≈32 RPM，周期 ≈1.875 s），否则 256 RPM 频闪、低速看似静止。

**每帧成本**：静态部分与现状持平（零 tessellate）+ M × 2~6 µs（估算）→ M=100 约 0.2~0.6 ms，M=1000 约 2~6 ms。

**硬性要求**：**必须为动态格保留每-state 静态 SBB 回退**，否则代理失败 = 整格消失。

## 4. P8：手持/物品栏真实预览

可行性 **A-（1.5~3 人日）**。推荐路线：`ModelEvent.ModifyBakingResult` 换物品 BakedModel（覆写 `isCustomRenderer()→true` 与 `applyTransform()→return this`）+ `RegisterClientExtensionsEvent.registerItem` + 复用 P6 的 baker/render。

**不要**改物品 JSON 为 `"parent":"builtin/entity"`：能跑，但无几何 → 降级时物品**直接隐形**，还得手抄 display 段。

三条硬事实：
1. `BlockRenderDispatcher` 对 `ENTITYBLOCK_ANIMATED` 会用**零组件空壳 stack + `ItemDisplayContext.NONE`** 反向回调 `renderByItem`——这是"无限递归"真身，降级分支**禁止**再调 `renderSingleBlock`/`ItemRenderer.render`；
2. `BakedModelWrapper.applyTransform` 默认返回原模型 → **不覆写则 `renderByItem` 永不调用且零报错**；
3. quads 烘焙时已 /16 成 0..1 空间 → 物品侧只需 `translate(0.5,0.5,0.5)` 抵消 `ItemRenderer` 的 `translate(-0.5,-0.5,-0.5)`，即可**逐行复用** `BOX_PX/BOTTOM_PX/offset/scale` 数学。

**最大坑**：GUI 里 `renderByItem` 抛异常 = **直接崩游戏**（`GuiGraphics` ReportedException）→ 全吞异常；`VirtualRenderWorld` 构造首指令解引用 level（已字节码实测 NPE）→ `level==null` 必须降级画原机壳。

**需人眼验收**：GUI 里 12px 内腔 × 0.625 ≈ **7.5 屏幕像素**，预览可能偏小，待定是否给 GUI 上下文放大。

## 5. P9（可选）：动态第二期 A2 + 补齐静态缺件

**当前静态预览本就缺件**（可直接验收的既有问题）：风扇**无叶片**（`encased_fan/block.json` 只有外壳，叶片在 `AllPartialModels.ENCASED_FAN_INNER`）、压机无压头、搅拌机无杆无头、磨石无内盘、锯无锯片、皮带无带面。

A2 路线：常驻 `VirtualRenderWorld` + 代理 BE，每帧直接调 Create 注册的 BER，每游戏 tick `smart.tick()` 一次。**比 PE 省事**：Create 6.0.10 里 11 类部件**全都有注册 BER**，不必像 PE 那样手写 partial 表。但需要**每格客户端 NBT**（`Speed`/`Source`/`Network`），且**必须做 `Source` 坐标重基**，否则变速箱/离合转向符号错。皮带是已知陷阱（PE 为此重写了整个 belt renderer）。

## 6. 风险与验收总表

| 功能 | 主要风险 | 人眼验收点 |
|:--|:--|:--|
| P5 玻璃包壳 | cube_all 挡死预览；multipart/属性写错整块加载失败；共面闪烁 | 无边框形态只剩底座；包壳后是边框玻璃材质、预览仍可见；去壳手势顺手 |
| P7 动态 | 转速采集时机（未确认）；动态格失败致整格消失（须静态回退） | 轴/齿轮/粉碎轮真的在转；速度感不频闪也不像静止 |
| P8 手持 | GUI 异常崩游戏；缓存键带 light 每帧重烘 | 手持/物品栏出现真实预览；GUI 里尺寸是否可辨 |
| P9 二期 | 每格 NBT 体积冲击同步包（未实测）；皮带必须自写 | 风扇有叶片、压机有压头、锯有锯片 |

**顺带的技术债**：烘焙用的 catnip `ShadedBlockSbbBuilder` 在 ponder 1.0.82 已标 `@Deprecated(forRemoval=true)`——当前可用，建议收敛到单点使用，将来集中替换。
