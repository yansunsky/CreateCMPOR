## 三、两个方块

### 应力拓展方块 `createcmpor:stress_extension`
- **外观**：完全复用安山传动箱（`create:andesite_encased_shaft`）的模型/纹理/旋转杆渲染。
- **类结构**：`StressExtensionBlock extends RotatedPillarKineticBlock implements IBE` + `StressExtensionBlockEntity extends GeneratingKineticBlockEntity`。
- **面功能**：
  - 轴向两端（上下面）：应力接口面，可接传动杆接入 Create 应力网络。
  - 其余四面：通过 NeoForge capability 代理，把紧贴的 CMPOR 工厂方块的物品/流体/能量 handler 转发到自身（指向同一底层容器），实现工厂 IO 拓展。

### 应力 I/O 方块 `createcmpor:stress_io`
- **外观**：复用创造马达（`create:creative_motor`）的模型/纹理。
- **类结构**：`StressIOBlock extends DirectionalKineticBlock implements IBE`（含 `powered` 激活态）+ `StressIOBlockEntity extends GeneratingKineticBlockEntity`。
- **激活**：默认不激活，空手右键切换激活/停用。
- **工作原理**：激活后读本地应力网络盈亏——网络缺应力（余量<0）时作输入端提供类创造马达应力源；有余量时作输出端可向外供应力。
- **配置** `enableStressOutput`（默认 true）：
  - true：应力>0 时向外提供，同时处理<0 的输入。
  - false：禁止输出，仅在应力<0 时从外部吸取。

## 四、关键设计决策（与计划书的差异）

计划书设想内部 IO 方块与外部拓展方块「实时配对、指向同一内存地址、实时传应力」。但源码分析表明 **CMPOR 是「评估→固化」两阶段系统**：

- 评估期：压缩空间内 IO 方块仅在玩家触发评估的 ~300 秒内激活，作用是**记账**（记录每秒 IO 速率），不与外部实时交换。
- 固化后：`FactoryBlock` 替换评估方块，**完全自包含**地按录得 pattern 循环吞吐，与压缩空间彻底解耦，**无任何内外实时通道**。

因此计划书设想的实时配对机制在 CMPOR 中并不存在。经与用户确认，采用「**应力作为工厂第四种资源**」架构：把 Create 应力当作类似 CMPOR 现有能量通道的资源，集成**在固化后的工厂方块上生效**——应力拓展方块作为外部桥梁读写工厂 IO，与 CMPOR 原有的物品/流体/能量通道同构。

由于 CMPOR 工厂容器为 private 且无扩展 API，本模组**不修改 CMPOR 源码**，集成逻辑全部在附属模组侧完成。

## 五、当前版本范围与后续迭代

**已实现（v0.1.0）**：
- 两个方块的注册、外观渲染、创造物品栏。
- 应力拓展方块接入 Create 应力网络，读取网络应力/容量/余量；四侧 capability 代理转发相邻工厂 IO。
- 应力 IO 方块的激活机制、输入/输出模式判定、`enableStressOutput` 配置。
- 编译通过、runClient 启动验证通过。

**后续迭代目标**：
- 内部应力 IO 方块 ↔ 外部应力拓展方块的**完整跨维度配对**（通过 `Core.getMachine(roomCode)`/`Machine.TargetPos` 建立内外联系）。当前两方块各自功能正确、独立工作；跨维度联动因 CMPOR 无扩展 API、涉及跨维度状态同步，留待迭代。
- 在固化工厂上注入「应力 pattern」（需 CMPOR 提供扩展点或额外 mixin）。
- 应力数值平衡与 GUI/Goggle 信息展示。
